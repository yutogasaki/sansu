# 「ちいさな遊園地」GPT画像制作・Blender立体化・アプリ連携 指示書

作成日：2026-09-05  
版：Draft v0.2 — 制作開始用の改訂案。美術承認・モデル完成・実機検証済みを意味しない。  
対象：企画者、画像生成担当、Blender制作者、UI／実装担当。

## 0. この指示書の結論

**色付き樹脂の厚みと、少量の木の温かみを持つ「組み替えて遊べる卓上玩具」を作る。GPTでは見た目の基準を作り、Blenderでは同じ人形・同じ遊具を再利用可能な立体として作る。アプリには、固定視点から書き出した部品画像と動作素材を組み込む。**

目標は「遊園地のきれいな絵」ではない。**置き方を変えると人形の動きが変わり、自分でも触って試したくなる、小さな動く玩具**である。

制作の順序：

**GPTの全体見本 → 人形・遊具の単体資料 → Blenderの簡易立体と画角確認 → 本制作 → 2配置の動作・合成検証 → 量産・アプリ組み込み**

最初から全6種、全ポーズ、自由視点の3Dゲームを作らない。最初の完成単位は、人形1体、すべり台、トランポリン、シャボンゲート、3位置の台座、泡の代表表現である。

### 表記

| 表記 | 意味 |
|---|---|
| **固定条件** | 今回維持するゲーム規則と制作境界。変更は製品仕様側の判断が必要 |
| **提案** | v0.2で用意した初期既定値。これを起点に制作し、検証で必要な箇所だけ変える |

提案値を実測値・最適値と呼ばない。単に「要決定」と残すのではなく、誰が・何を見て・どの段階までに決めるかを末尾に記す。

## 1. 目的と、今回変えない範囲

### 1.1 子どもに伝わってほしいこと

静止時には「ここで、この人形を遊ばせられる」と分かる。動作時には「ここを通ったから泡が付いた」「先に跳んだからゲートを越した」と分かる。編集時には「これをこっちへ置いたらどうなる？」と試せる。

面白さの中心を、全画面の紙吹雪や報酬表示へ移さない。厚み、触感、接触、人形の重心移動、予想と結果の違いを見どころにする。

### 1.2 固定条件

- 最初は横方向の3位置。すべり台とトランポリンを1個ずつ所有し、学習前に完成済みコースを再演できる。初期配置は「すべり台 → トランポリン → 空き」。
- 最大3コース、各6位置。個体として持つ部品を配置する。精密なドラッグを必須にせず、部品と設置場所のタップで操作できる。
- 配置編集と再演は無料。再演中の見た目が、確定した配置とゲーム状態を勝手に変えない。
- 動きは配置とゲーム規則から決まり、学習の正誤、回答速度、抽選でジャンプの結果を変えない。
- 予約した学習区間の完了で、選んだ部品を1個制作できる。支援込みの完了と、独力の習得を分ける。
- 誤答、中断、スキップで人形を痛がらせず、部品を壊さない。未完の制作・学習、既存作品、所有状態を保持する。
- 学習中は遊園地の動きとゲーム音を止める。問題・筆算・分数・複数欄・選択肢・支援表示を優先し、美術へ問題文や正答を焼き込まない。
- 英語の既存範囲は中学生向け単語4択。幼児向け音声教材や発音評価を実装済みとは扱わない。

### 1.3 3Dの扱い

**提案：Blenderを制作道具として使い、アプリの表示は固定視点の2D素材を第一経路とする。** `.blend` は編集用の立体原本であり、アプリにそのまま読み込ませる納品形式ではない。

リアルタイム3D、自由なカメラ回転、3D物理、GLB納品の必須化は今回の範囲外。2D素材では表現が成立しないと分かった場合に、描画方式の変更を別途判断する。MVP仕様の「3Dを作らない」は、「リアルタイム3Dは対象外。Blenderによる素材制作は許可」と区別して更新する案とする。

### 1.4 資料の優先順位と未確認事項

今回提示されたv0.1の固定条件を、この改稿の前提とする。本チャットにある `22_SHARED_SUBJECT_BUILD_AND_PLAY_SPEC.md` は未実装・未採用と記された提案版であり、最新リポジトリの正本と同一の版だとは断定しない。

制作開始時に実装担当が、最新版22、`simulation.ts`、MVP監査の版を照合する。差分は短い一覧に残す。本書のために現在のアプリや公開設定を変更しない。提示された相対リンクの監査画像・ソースコードは、この改稿では直接検査していない。

## 2. 美術方針：色付き樹脂を主役に、木を脇役にする

### 2.1 一文の制作方針

**つまめそうな厚い遊具、見守りたくなる小さな人形、ぱちんとはじける軽い泡。その三つが主役の、明るく少しへんてこな卓上遊園地。**

v0.1の「木＋樹脂」を維持しつつ、全体をベージュの知育玩具へ寄せすぎない。遊具の働きが見える、はっきりした形と色を優先する。大人向けの静物写真として整っていても、遊ぶ場所や動きが弱い案は採らない。

### 2.2 造形の約束

| 要素 | 今回の制作案 | 避けるもの |
|---|---|---|
| 全体 | 大きな面、厚い縁、丸い接合部。単体の輪郭で機能が分かる | 薄い板、細い線、箱と球を未調整で並べただけの形 |
| 木 | 台座の側面、すべり台の支柱など、支える場所に限定 | 全面の木目、年輪の大きなノイズ、汚れや傷の誇張 |
| 樹脂 | 遊具の主役。半艶で、縁に丸いハイライトがある | 全素材の鏡面化、白飛び、重い金属感 |
| 柔らかい面 | トランポリンやマットは少し沈む、戻る | 鋭いばね、露出機構、硬い激突 |
| 人形 | 小さくても頭・胴・足の区別と重心が読める | 記号のような棒人間、細い指、顔の情報過多 |
| 泡 | 薄い輪郭、少数の反射、ほぼ透明な中心 | 分厚いガラス、水槽、顔を隠す白濁 |
| 背景 | 台座が接地した、簡潔な玩具の舞台 | 観覧車・建物・雲など、未実装の遊びを約束する飾り |

### 2.3 初期配色案

以下は色の役割を固定するための出発点。材質のRGBへ機械的に転記しただけで仕上がり一致とはしない。最終色は同じ照明・表示変換で確認する。

| 役割 | 提案色 | 主な用途 |
|---|---|---|
| 背景 | ミルク色 `#F6F0E6` | 背景、余白 |
| 支える素材 | 明るい木色 `#D7B58D` | 台座側面、支柱 |
| すべる・勢い | コーラル `#EE7964` | すべり面 |
| 跳ねる | 青緑 `#3B9F9A` | トランポリン枠 |
| 通る・変化 | バター黄 `#EFC95A` | シャボンゲート枠 |
| 人形の主色 | 青紫 `#777BC3` | 胴・靴などの大きな面 |
| 顔・輪郭の要所 | 深い青灰 `#283B4B` | 目、口、必要なコントラスト |

全部品に全色を使わない。色だけで機能や選択状態を区別せず、輪郭・凹凸・動作を併用する。人形の顔が隣の遊具へ埋もれる場合は、背景よりも人形・遊具の明度関係を先に直す。

### 2.4 人形の第一制作案

**提案：2.2〜2.4頭身程度の、短い手足を持つオリジナル玩具人形。** 頭は角のない豆形、足は接地が分かる丸い靴。輪郭の特徴は、額の片側にある小さな丸い突起など一つに絞る。既存キャラ名、ポッコ、黄色い体を前提にしない。

人形を「球体に大きな目と赤い頬を付けたもの」にしない。待機時は軽く前を向き、踏み込みで重心が下がり、跳躍時は手足が開く。顔は正面立ち絵だけでなく、アプリのカメラから64px程度で読めることを確認する。

進行方向は+X。頭の向きは、動作を阻害しない範囲で少しカメラへ開ける。真横の顔に無理に両目を貼り足すなど、視点ごとの矛盾で解決しない。

人形の最終輪郭・顔・配色は画像選定で決定する。名前はモデル制作の開始条件にしない。

## 3. GPT画像制作：見た目の基準と、立体の原本を分ける

### 3.1 GPTに任せるもの／任せないもの

| GPTで決める | Blenderで確定する |
|---|---|
| 雰囲気、輪郭、配色、素材感、表情、主役の大きさ | 実際の厚み、寸法、裏面、接合、通路、カメラ |
| 完成時に欲しい見た目 | 同じモデルで再現可能な複数配置・複数ポーズ |
| 単体の形を読み取りやすい参考画像 | 編集可能なメッシュ、原点、リグ、アニメーション |

GPT画像を一枚の板に貼った `.blend` は、立体化の納品としない。自動Image-to-3Dを使う場合も中間素材として扱い、人形と遊具が融合していないか、穴が塞がっていないか、背景がメッシュ化されていないかを検査する。特定の外部サービスが使えることや、自動変換だけで完成することは前提にしない。

### 3.2 最初に必要な画像

| ID | 内容 | 目的 |
|---|---|---|
| `REF-01` | 全体見本1枚。制作後の3位置コース | 質感、主役、画角、空間の方向を選ぶ |
| `REF-02` | 同じ人形の単体画像 | 輪郭、顔、体の比率を決める |
| `REF-03` | 同じすべり台の単体画像 | 入口、階段、すべり面、出口を読む |
| `REF-04` | 同じトランポリンの単体画像 | 面、縁、脚、沈む場所を読む |
| `REF-05` | 同じシャボンゲートの単体画像 | 開口、フレーム、地上通過の形を読む |

最初から全種一覧、全ポーズ、全色を一枚へ詰め込まない。まず全体の方向を選び、その採用画像を添付して単体画像を作る。画像ごとに形を再発明しない。

必要な背面や側面は、その後に補助資料として追加する。GPTの複数視点は正確な三面図とは扱わない。OpenAI公式資料でも、複数生成間の同一性や厳密な構図には限界が明記されている。[S1]

### 3.3 参照画像の管理

`reference-index.md` に、画像ID、実ファイル名、生成／取得日、入力に使った参照画像、指示文、採用する特徴、変えてよい特徴、承認状態を残す。第三者画像を追加する場合は出典と利用条件も記録する。

**今回の改稿時点で承認済み画像は0枚。** 候補を作っただけで「採用済み」にしない。寸法の矛盾が出たら、ゲーム機能と承認済みの形の特徴を守りつつ、Blenderのモデルで整理する。背面まで再生成画像へ無条件に合わせない。

Blenderの造形を採用した後は、同じモデルから正面・側面・背面の資料をレンダーする。以降の幾何形状の原本はそのモデルとする。

## 4. カメラと寸法：本制作前に必ず合わせる

### 4.1 真横のゲート問題を解く

進行方向が+X、ゲートの穴がYZ平面、カメラが-Y側から真横を見る場合、穴はほぼ縁しか見えない。俯角を付けるだけでは、この問題は解決しない。

**提案：軽く斜めから見る固定の平行投影とし、ゲートの輪も少しカメラへ開く。** 「X方向が画面の右へ進む」は維持するが、「床上の進行線が完全な水平」は必須にしない。

| 項目 | 最初の検証値 |
|---|---|
| 軸 | +X＝進行、+Y＝奥、+Z＝上 |
| 投影 | 平行投影。距離より投影スケールで見かけの大きさを管理する [S2] |
| カメラ | -Y側を基準に、+X側へ25°回り込み、水平面から15°見下ろす。ロール0° |
| ゲート | 輪の法線を+Xから-Yへ15°向け、穴をカメラ側へ少し開く |
| 被写界深度 | 本番部品素材では使わない |
| モーションブラー | 本番の基準素材では使わない |
| 光 | カメラ左上寄りからの大きな柔らかい主光源と弱い環境光。全素材で共通 |

この25°／15°は見本の提案であり、固定済みのカメラではない。人形が穴を通って見えるか、跳躍が高さとして読めるかを、簡易立体で確認してから固定する。必要なら輪の向きとカメラを同時に修正する。

### 4.2 人形を単位にした寸法案

単位Uは「待機時の人形の全高」。制作ファイルでは仮に1U＝1 Blender unitとし、現実の1mの玩具という意味にしない。全素材のスケールを統一する。

| 対象 | 提案寸法・条件 |
|---|---|
| 人形 | 全高1U、胴を含む横幅の目安0.45〜0.55U |
| 位置の間隔 | 中心間1.5U |
| すべり台 | X方向の本体幅1.35U以内、すべり始めの面は約0.65〜0.75U。入口は-X、出口は+X |
| トランポリン | 本体幅約1.0〜1.2U、通常面の高さ約0.15U |
| ゲート | 外形の高さ約1.45U、開口の高さ1.2U以上。開口幅は人形の腕を含む通過姿勢＋余裕で決める |
| 台座 | Z＝0が設置上面。厚みは約0.15〜0.2U |
| 端の余裕 | 最初は左右約0.55Uずつ。実際の待機・着地姿勢を含めて調整 |
| 高跳躍 | 足元の頂点を約1.9Uから試す。ただし下記の通過余裕が優先 |

モデルは単なる外形ではなく、動作のための空間も持つ。すべり台の入口まで歩けるか、座ってすべる腰と手すりが干渉しないか、トランポリンの面に足が触れるかを確認する。

**飛び越しの受入条件：** 飛び越す部品の上を通過する全区間で、人形・泡の最下部が、部品の最上部より上にある。足元だけを見て合格にしない。初期の空間余裕は0.1Uを目安にし、全6種の最大外形に対して量産前に再確認する。

### 4.3 画面との整合を先に確認する

390px幅に左右16pxの余白を取ると、舞台の幅は358px。人形を72px相当で見せるなら、同じ投影上で使える横幅は、人形高の約5倍に限られる。3位置、入口、着地点を無制限に広げて、同時に人形を80pxにすることはできない。

**提案：スマートフォンの3位置全景は人形高64px前後を出発点にし、80pxは拡大時の候補とする。** 実際には俯角・ヨー・ポーズの投影を含めて測る。見本を縮小して済ませず、同じモデルの実寸レンダーで決める。

カメラを決めたら、設定名 `CAM_PARK_MAIN`、投影方式、位置、回転、投影スケール、解像度、床上の原点、光源、表示変換を保存する。部品単体の書き出しのたびに、画角や照明を変えない。

## 5. 390×844の画面構成案

以下はCSSピクセルでの基準アプリ領域案。ブラウザのツールバー高と混同せず、実装では表示領域とsafe-areaに追従する。

| 領域 | 仮の範囲 | 内容 |
|---|---|---|
| ヘッダー | y＝0〜64 | 戻る／作品名など。情報は最少 |
| 舞台 | y＝64〜494 | 人形、遊具、跳躍空間、台座、安全な終点 |
| 主操作 | y＝494〜566 | 試遊時は「もういっかい／とめる」、編集時は配置・試遊の主操作 |
| 部品棚 | y＝566〜774 | 所有部品、選択状態、制作対象。棚だけで必要なスクロールを受ける |
| 下端余裕 | y＝774〜844 | safe-areaなどに割り当てる仮の余裕 |

台座を画面の底へ小さく追いやらない。舞台内の足元基線を下寄りに置き、上を高跳躍の空間として確保する。操作面は舞台の一部として色・縁の形を合わせるが、UI文字・ボタンはレンダーに焼かず、アプリ側のUIとして置く。

部品の見た目より押せる領域を大きく取れるようにする。タップ領域は少なくとも48CSS px四方を初期目標にし、実寸で隣接操作の誤りを観察する。これは本プロジェクトの提案値であり、子ども全員に適するという保証ではない。

### 5.1 3位置から6位置への拡張

**提案：人形を縮めず、横に長い同じ舞台の一部を表示する。** 編集時は左右の移動操作とドラッグを用意するが、ドラッグだけを必須にしない。試遊時は行き先を先に見せる、短い横追従を使う。

高跳躍では踏み切り位置、飛び越す位置、着地位置の3位置が読める範囲を優先する。ジャンプ中に着地点が初めて現れる急な追従は避ける。全体を見る操作は任意にし、全景で小さくなる状態を主たる試遊画面にしない。

768×1024では、単純な縦横倍率の拡大だけでなく、舞台幅と棚の配置を調整する。人形と遊具の相対尺度は変えない。6位置表示は段階Bで静止配置だけでも先に試し、全6種の量産後まで後回しにしない。

### 5.2 学習画面

制作対象の小さな静止サムネイルだけを残し、問題画面へ切り替える。分数、筆算、multi、英語4択、支援表示をそれぞれ当てて確認する。学習欄を狭めて舞台を常時残すことはしない。

## 6. 部品・動作の制作範囲

### 6.1 最初に作るもの

| ID | 必要な立体・状態 | 基準点・確認箇所 |
|---|---|---|
| `actor` | 1体。待機と代表ポーズ。動作検証で歩く・すべる・踏み込む・空中・着地へ追加 | 足元基準、腰、頭、足先。小さな表示での顔 |
| `slide` | 入口、階段、上部、すべり面、出口、必要な手すり | entry、sit、exit。座る経路とすべる向き |
| `trampoline` | 枠と脚は固定、踏む面は変形可能 | contact、takeoff、landing。通常／沈む／戻る |
| `bubble-gate` | 厚い輪と支持部。前後を分けられる構成 | enter、cross、exit。開口と遮蔽 |
| `stage` | 3位置、スタート、柔らかい終点 | 各位置の設置面中心、開始／終了点 |
| `bubble-fx` | 輪郭、反射、前後、破裂。人形と別 | 人形に対する中心と大きさ。地上／空中／着地 |

### 6.2 採用後に増やすもの

減速マットは踏む面が少し沈み、歩みの変化を見せる。ベルは接触で揺れ、無音でも鳴ったことが分かる。色ゲートは人形の色の変化と、その後の泡の色へつなぐ。ベルへ飛び越し反応を足したり、色を正解・不正解の印へ転用したりしない。

色バリエーションは全ポーズを一斉に増やさず、まず通常色と変更色1例で検証する。顔・目・靴など色を守る領域を分け、全身への単純な色フィルタで顔を壊さない。マスク方式か色別レンダーかは、この例で選ぶ。

### 6.3 人形の演技

動作は「予備動作 → 接触 → 反応 → 収まり」を基本にする。踏み込みで膝や胴が縮み、跳躍では手足が開き、着地では重心が一度沈んで戻る。全身の上下移動だけで代用しない。

リグは、この動きに必要な最小構成でよい。指の細かな骨、複雑な顔リグ、衣服の物理は初期に作らない。手足が独立して動き、頭・胴の向きが少し変わる構成を優先する。リグ方式より、編集可能性と代表動作の読みやすさを受入基準にする。

## 7. 見せる因果と、アニメーションの契約

### 7.1 必須の比較

| 場面 | 見えること | 禁止する見た目 |
|---|---|---|
| すべり台 → トランポリン → ゲート | 力強く踏む、ゲートの上を越す、泡なしで着地 | ゲートをすり抜ける軌道、飛び越しで泡が付く |
| すべり台 → ゲート → トランポリン | 地上で泡が付き、泡を保って跳び、着地ではじける | 頂点で早くはじける、泡が後から瞬間移動で追う |
| 勢いが弱いトランポリン | 同じ位置で小さく跳ぶ | 隣へ移る、高跳躍と同じ見た目 |
| 高く跳んだ先に部品 | 着地した位置の部品に反応する | 飛び越した部品の反応も一緒に再生する |
| 最終位置から高跳躍 | 画面内の終点に柔らかく着地する | 台座の外へ落下、姿が消える |
| 泡のまま地上で終了 | 泡を保ったまま落ち着く | 演出の都合で勝手にはじける |

「着地する位置に次のトランポリンがある」「連続したゲート」「停止して編集へ戻る」ときの論理順序は最新のゲーム側に合わせる。未定義なら実装担当が仕様判断を求め、美術担当が結果を補わない。

### 7.2 位置の移動と、体のポーズを分ける

**ゲーム側が経路とイベントを決め、アニメーションはその結果を見せる。** アニメの終了通知を根拠に、泡の付与や制作物の取得を保存しない。

提案する階層は、`ROOT_PATH`＝コース上の移動、`ROOT_POSE`＝体の傾きや踏み込み、各骨＝手足・頭。アプリ側で移動する人形素材へ、もう一度同じ前進量を焼き込まない。

同じモデルの動作見本では経路を含めて再生する。本番素材は原則として足元基準の局所動作として書き出し、アプリで経路に乗せる。すべり台の座面など、経路が特殊な部分は基準点と補助経路をセットで持たせる。

### 7.3 イベントの意味を合わせる

`contact`、`takeoff`、`apex`、`land`、`bubble_attach`、`bubble_pop`、`settle` を制作側の意味ラベルとする。既存API名とは限らないため、実装担当が対応表を作る。

動作素材には、フレームまたは時刻、基準点、イベントの意味を記録する。遅い端末で描画フレームが飛んでも、イベントはゲームの確定した時刻・順序に従う。停止・再開・途中位置への復元でも二重に反応を実行しない。

**提案：動作確認の原本は24fpsで制作を始める。** 本番スプライトのフレーム数とアプリの描画更新頻度は別に決める。歩きのループ、踏み込み、空中、着地をそれぞれ評価し、既存MVPの尺へ無理に押し込まない。

動きを減らす設定では、余分な跳ね返り・画面揺れ・追従の加速度を減らす。ただし「通った／越した／着地した」の順序は残す。結果だけへ瞬間移動して因果を消さない。

## 8. 本番素材の分割と合成

### 8.1 基本構成

| レイヤー | 内容 |
|---|---|
| 背景／空台座 | 固定の背景と設置面。隣接部品の固有影を含めない |
| 部品の地面影 | 接地を示す短い影。隣に別部品が来ても破綻しないもの |
| 部品の奥側 | ゲート後半、手すりの奥側など |
| 人形の地面影 | 人形の真下の設置面側へ配置。空中で人形と一緒に上げない |
| 泡の奥側 | 人形の後ろを通る輪郭・反射 |
| 人形 | ポーズ・表情・色の必要な範囲 |
| 部品の手前側 | ゲート前半や手前の手すり。該当する通過時に遮蔽 |
| 泡の手前側／反応 | 輪郭、反射、破裂など。顔の読みやすさを保つ |

この表は常に固定の描画順という意味ではない。人形がゲートの手前、内側、通過後、上空のどこにいるかで、前景部品との関係を変える。複数の部品が画面上で重なる場合も、位置と通過状態から順序を決める。

**最初に検証する遮蔽はゲートだけでなく、すべり台の手前の縁も含む。** 人形が遊具へ乗っているとき、常に最前面へ描いて済ませない。

### 8.2 合成用の見本を原本にする

通常の一括3Dレンダーと、独立画像の貼り合わせは、相互の影・反射・屈折まで自動的に一致するものとは扱わない。

採用基準用に `assembly-reference` を作り、本番と同じ分割・合成条件で見た目を確認する。別途、雰囲気確認の `beauty-render` を作ってもよいが、本番で再現しない反射や隣への濃い落ち影に魅力を依存させない。

合成では、接地、輪郭、顔、素材の厚みが保たれることを優先する。写実的な相互反射を諦める場合は意図した表現上の制約として記録し、完成見本との差を隠さない。

### 8.3 泡は「背景を屈折させるガラス球」にしない

**提案：中心はほぼ透明、輪郭に淡い色、数か所の反射で見せる、合成向けの泡。** 任意の人形・背景に重ねる用途では、この方式を第一候補とする。1枚の透過画像で、背景に応じた本物の屈折まで再現する仕様にはしない。

通常の人形／色付き人形、明るい下地／暗い下地、地上／空中で確認する。人形の顔が見え、泡が前後に回り込んで見えること。破裂は顔を完全に覆う白フラッシュではなく、輪郭がほどけて小さく散る方向を試す。

### 8.4 基準点と切り抜き

部品の原点は設置面中心、人形の原点は足元基準、泡は人形に対する基準とする。素材ごとに画像の左上を「置く場所」にしない。

PNGをフレームごとに切り詰める場合は、元キャンバス、切り抜き矩形、元キャンバスでのpivotを保存する。アプリはこの情報を使って戻す。歩くたびに基準点や人形の大きさが揺れる素材は不合格。

カメラの斜め角度を採用するため、配置はX座標の単純な横移動だけでは足りない。Blenderの投影から出した各設置点・接触点を使うか、同等の座標変換を一つにまとめる。UI実装者が目分量で素材ごとに補正しない。

## 9. `.blend` と書き出しの納品契約

### 9.1 制作データ

人形、各遊具、台座、FX、カメラ、照明、書き出し用設定を区別できるCollectionにする。意味のない既定名だけで納品しない。

| 名前の例 | 中身 |
|---|---|
| `CHAR_actor` | 立体、材質、リグ、動作 |
| `PROP_slide` / `PROP_trampoline` / `PROP_bubble_gate` | 各遊具の立体と必要な可動部 |
| `STAGE_course` | 台座、設置点、開始／終了点 |
| `FX_bubble` | 泡、反射、破裂 |
| `RIG_camera_lights` | 本番カメラ、共通照明 |
| `REF_images` | 承認済み画像。参照として非表示にできる |

オブジェクトは個別に選択・移動・再配置できる。原本と書き出し用の複製を必要に応じて分け、リグ済みオブジェクトへ不用意に変換を適用して壊さない。使用するBlenderの正確な版・描画エンジン・依存アドオンを記録する。

既存環境がある場合は、その互換性確認を先に行い、最新版へ無断更新しない。外部テクスチャは同梱または対応するパックを行い、全外部依存が自動的に含まれたと決めつけず、別フォルダへコピーして開けるか確認する。

### 9.2 書き出し

| 項目 | 提案 |
|---|---|
| 立体原本 | 編集可能な `.blend`。参照画像、外部テクスチャ、再出力手順を添付 |
| 全体見本 | PNG。UIなしの舞台と、別途UIへ当てた確認画像を区別 |
| 透過素材 | PNG RGBA。Filmの背景透過と、出力のアルファ保存の両方を確認 [S3][S4] |
| 解像度 | 実表示の約2倍を出発点とし、ポーズの余白を確保。一律4Kにしない |
| 動作見本 | MP4。音なしで因果が分かるもの |
| 色 | 共通の表示変換・露出を固定。sRGB表示用PNGをアプリで再度トーン変換しない [S5] |
| 透明縁 | 納品PNGのアルファの扱いを記録。アトラス化・読み込み時に二重の乗算で黒縁を作らない |
| 配信素材 | 実装側で圧縮・アトラス化。元PNGと対応関係を残す |

PNGの目視確認は白い下地だけで済ませない。明暗2色、実際の台座、人形の通常色と変更色で見る。アトラス化ではフレームの端から隣の画像がにじまない余白を設け、その幅は使用する描画設定で確認する。

### 9.3 素材一覧の必須情報

ファイル名、asset ID、state、variant、source revision、camera ID、画像寸法、元キャンバス寸法、crop、pivot、pixels-per-unit、フレーム数、フレーム時間、loop、イベント、前後レイヤー、alpha方式、色設定、転送容量を一覧化する。該当しない項目は空欄ではなくN/Aとする。

命名案は `park-<candidate>-<asset>-<state>-<variant>-<frame>.png`。例のcandidate IDを、承認済みのIDと誤認しない。stage素材とactor素材の版が混在したら検査で分かるようにする。

### 9.4 容量と再生

PNGやWebPの転送容量だけでなく、展開後の画像メモリを記録する。例えば256×256のRGBAフレーム100枚は、ピクセルデータだけでも `256×256×4×100＝26,214,400 bytes`、約25MiBになる。アトラス余白、GPU側の複製、その他の画像は別途必要である。

提案する初期の警戒線は、初回表示に必要な追加美術の転送約4MB、現在のコース用素材の展開後ピクセルデータ約64MiB。端末で検証して確定するための目安であり、既に達成済みの予算ではない。

全キャラ色×全動作×全フレームを初回に読み込まない。現在のコースを優先し、同じ部品を複数置くときは素材を共有する。素材が未着のまま、論理と違う別の泡や別のポーズを表示して再生しない。

## 10. 制作段階と、その場で必要な証拠

| 段階 | 制作物 | 次へ進む条件 |
|---|---|---|
| **A0：画像で方向を決める** | 全体見本、同じ人形、初期3部品の単体参考、参照一覧 | 企画者が輪郭・素材・配色・主役の大きさを選ぶ。立体の寸法承認ではない |
| **A1：簡易立体で成立を確認** | 編集可能な簡易 `.blend`、初期／制作後の配置、代表ポーズ、ゲート通過／飛び越しの確認 | 画角、足元、開口、跳躍、端の着地が成立。数値と基準点を記録 |
| **A2：本制作** | 人形・初期3部品・台座・泡の完成版、同じモデルの資料、合成前提の完成見本 | GPT基準の良さを保ち、64px表示でも顔・素材・働きが読める |
| **B：動作・合成・アプリ確認** | 2配置の無音動画、分割素材、再合成、代表動作、色変更1例、実画面 | 390×844と768×1024で任意配置と因果が保たれる。6位置表示案も確認 |
| **C：必要分だけ量産** | 追加3部品、承認済みの全動作、棚・サムネイル、配信素材・一覧 | 容量・端末・復元・配信確認を終える |

A0の承認前に全モデルを作り切らない。A1の寸法確認前に質感を磨き込まない。Bの合成確認前に全フレームと色違いを量産しない。

段階Aの範囲へ全リグ・全6種・GLB・全端末の最適化を混ぜない。一方、Bで必要になる前後分割・原点・可動面はA1の段階で作れる構造にする。

## 11. 受入条件

### 11.1 美術と立体

「かわいい」「高品質」という言葉だけでは承認しない。参照画像、Blender画像、実寸画面を同じ表示寸法で比べる。

| 判定 | 合格を判断する証拠 |
|---|---|
| 主役 | 初期画面で人形と試遊する場所が見つかる。顔が光・泡・UIに隠れない |
| 機能 | すべり面、踏む面、通り抜ける穴が文字なしで区別できる |
| 触感 | 木・樹脂・柔らかい面・泡が同じ艶と同じ厚みに見えない |
| 立体 | 台座・人形・遊具を個別に選択して動かせる。画像を貼った平面だけではない |
| 再現 | 同じカメラ・材質で初期配置と制作後配置を出せる。欠けた裏面や閉じた穴がない |

### 11.2 動作・合成

ゲート通過、飛び越し、弱い跳躍、終点、着地先の部品、泡の地上終了を別ケースとして確認する。ゲートの前後、すべり台の手すり、人形の地面影、泡の輪郭、フレームの基準点を録画で点検する。

手動のスクリーンショットだけでなく、実際のゲーム状態で2配置を再生して確認する。停止・再開・編集・再読み込みを行い、既存の学習記録・制作物付与へ影響がないことを検査する。

### 11.3 子どもの理解

先に2配置の正解を教えない。「もう一度やってみたい？」への肯定だけで面白さを判定しない。自由に触れる場面を設け、どこを見るか、自分から再演するか、一か所を置き替えるかを記録する。

説明の確認には「何が起きた？」「次はどこに置いてみる？」などを使う。幼児には言葉での説明だけを要求せず、指差しや操作も見る。理解、安全な印象、面白さ、学習を挟んだ継続は別の欄で評価する。

### 11.4 配信

対象URL、build revision、candidate ID、設定フラグ、素材の版、キャッシュ／PWAの更新状態を記録する。ローカルでレンダーできたことを、ユーザーが見るアプリへ反映された証拠にしない。

## 13. v0.1からの主な変更

「Blenderで作る」の前に、GPTの全体見本・単体資料・参照管理を追加した。GPT画像を厳密な三面図や完成メッシュとは扱わず、Blenderのモデルを形の原本にする。

「木＋樹脂」を、色付き樹脂が主役・木は支える部分へ限定する第一案へ具体化した。人形、配色、ゲートの形、作る順序に初期既定値を用意した。

真横のカメラではゲートの穴が見えにくい矛盾を明記し、カメラの回り込みと輪の向きを同時に決めるようにした。人形の表示高、3位置の横幅、始点・終点を一つの寸法問題として扱った。

完成レンダーの後に初めて合成を考えるのではなく、本制作の前に通路・原点・前後・可動面を確認する段階を追加した。影・屈折の完全再現ではなく、本番の分割合成で再現できる完成見本を承認基準にした。

根の移動とポーズを分け、動作のイベントとゲーム状態の責任を明示した。納品画像の容量だけでなく、展開後のメモリも確認するようにした。
