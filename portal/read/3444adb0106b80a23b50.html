02. コアシミュレーション

1. 最初にシミュレーションする範囲

S1は、水分と日当たり／植物と食料／道と輸送／住人の行動と共同生活／人口と地区拡張を接続する。昆虫の訪問は、この上に載る条件付き確率の例とする。虫が来ないと食料が作れない、という依存にはしない。

ゲーム内の状態が結果の原因であること。 学習後に再生する成功ムービーで、実際の供給・移動・人口変化を代用しない。

世界の単位

論理マップは正方格子、1チャンク16×16セル。S1は初期1＋接続可能2チャンクを用意する。チャンクは内部管理単位で、別ステージではない。座標は世界座標で保持し、隣へ移っても最初の場所と住人は残る。

セルは基盤地形（地面／水面、高さ）、植生・施設の占有、道・橋・水路の重ね合わせ、水分、日陰、通行量を持つ。S1の施設は論理上1セル、実際の絵はセル内に収める。見た目を理由に歩行判定を曖昧にしない。大きな建物の複数セル占有は後続。

配置物は静的な地形・タグ、可変の状態、できる行為を分ける。全ペアの専用イベントを書くのではなく、waterSource、shadeProvider、foodProducer、foodStore、seat、roadなどの能力を共有する。ただしタグがあるだけで、未実装の動作が自動的に生まれたと扱わない。

2. 時間・更新順

1 tick＝ゲーム内1秒。表示のフレーム数と分離する。等速／2倍速／一時停止を用意する。学習画面、設定、非表示タブ、アプリ中断では世界を止める。現実の時計から不在分を追いつかせない。

更新順は固定：

  • 入力コマンドを順番に検証・適用する。拒否時は状態を一切変更しない。
  • tickを進め、固定周期の天候を更新する。
  • 水路の接続、水分、日陰、作物成長を更新する。
  • 変更された経路と仕事の予約を再検証する。
  • 住人の意思決定・移動・受渡しを更新する。
  • 共同食の供給を計算し、地区の直近履歴を更新する。
  • 条件付き訪問と入居候補を評価する。
  • 集まり・発見ログ・成長表示を生成し、保存用revisionを確定する。

同時に発生した処理は、システム順→安定したentityId順で処理する。カメラや描画品質を変えて結果を変えない。処理落ち時の追いつきは1フレーム最大5 tick。残りは実時間との差として捨て、長いフリーズから大量の出来事を一括発生させない。

3. 水分・日陰・植物

水分

clamp01(x)=min(1,max(0,x))。距離はセル中心のマンハッタン距離。水面または通水中の水路から最も強い影響を一つ採り、源の数を足し合わせない。

W = max over sources clamp01(1 - max(0,distance-1)/3)
S = max over trees clamp01(1 - distance/3)
M_target = clamp01(0.20 + 0.50*W + 0.08*S + weatherMoisture)
M_next = clamp01(M + 0.08*(M_target-M))

水源の隣はW=1、距離2は2/3、距離3は1/3、距離4以上は0。初期の水分は計算上の定常値を入れ、起動直後だけ作物が急変する状態を避ける。

地区の開拓時は新しいセルだけを定常値で初期化する。既存セルの水分は保持し、新地区の水源や木による水分への影響も次の論理tickから通常の緩和式で反映する。

「水路」は水源に接続し、上りにならない隣接セルを最大8辺までたどったものだけ通水する。輪を作っても水量を無限増殖させない。S1は水分供給を表す簡略モデルで、流量保存や本格的な水理計算はしない。水路が高地へ勝手に水を運ぶ見せ方にしない。水路自体は浅い溝として歩行を妨げない。

作物

waterFactor = clamp01((M-0.15)/(0.55-0.15))
            * clamp01((1.15-M)/(1.15-0.90))
lightFactor = weatherLight * (1 - 0.50*S)
growth += waterFactor*lightFactor / 120  # 毎tick

成長が1になり在庫に4個の空きがあれば収穫4個を在庫へ移し、growthから1を引く。満杯ならgrowth=1で止める。畑の在庫は8個。収穫は条件から安定的に起き、毎回の成功抽選にしない。天候によって速度は変わる。

畑を移すとgrowth・収穫済み在庫は保つ。環境値は新しい位置から計算し、過去の良条件を持ち運ばない。収納は状態を停止して保存する。再配置で再収穫、在庫リセットによる増殖、予約済み品の複製を起こさない。

見える結果

水路接続は水色の流れ、土の水分は地面の質感、作物成長は段階のある形、収穫済み在庫は実際のかごで示す。色だけでなく形・短い説明も使う。木を植えると日陰ができ、休める場所が増える一方、近くの畑の成長を遅くすることがある。

これはこの世界の簡略ルール。実在植物の育成条件を証明した教材として説明しない。後続で実在の生物名を使うときは、その条件説明を別途確認する。

4. 道・輸送・食料在庫

歩行グラフ

地面は歩行可能で1セル3秒、道・橋は1秒を基準とする。施設・木の占有セルと、水面は歩行不可。施設の入口は隣の1セルで定義し、到達可能性をそこで判定する。橋は水面上に置き、向かい合う両岸が地面または有効な橋へつながる場合のみ有効。

経路コストは次で計算する。

traffic = traffic*0.97 + このtickの通過重量
cost = baseCellSeconds * (1 + 0.75*clamp01(traffic/12))
通過重量: 徒歩1、台車2

複数住人の通行を排他的にロックしない。混雑は遅さ・迂回として現れ、永久渋滞や押し合いで詰まらない。経路を毎フレーム引き直さない。出発時、地形変更時、次の意思決定時に必要なものだけ再計算する。

輸送

畑→共同食の拠点（hub）へ、住人が荷物を運ぶ。食料は畑の在庫／住人の荷物／拠点の在庫のどこか一つに属する。アニメーションが終わったから別の食料を生成してはいけない。

通常は一回2個。台車を選び、畑と拠点の入口間が道・橋だけで連続していれば4個。同じ収穫4個を一回で運べるため、遠い畑では輸送回数を減らせる。台車は道のない経路では通常の手運びに戻る。道具の解放だけで全世界の生産速度を上げない。

拠点の容量は24個。空き容量と畑在庫を予約し、実際の受渡し時に一回だけ移す。行き先の予約がなくなれば再計画する。荷物を消したり、空中に放置したりしない。移動中の荷物は住人が持ったまま、別の有効な拠点へ運び直せる。

同時に配送する人数は max(1,floor(常住人口/3))。担当は生活の区切りで入れ替える。候補仕事は待ち時間が長いもの→移動コスト→安定IDで選ぶ。予約だけしたまま15 tick進めない仕事は解除して再計画する。出発後の正当な長距離移動にはこの15 tick制限を使わない。

拠点は担当住人の3食分＋次の収穫4個を目安に受入れを希望する。ただし容量を超えない。複数拠点がある場合、最初から町全体の食料を共有せず、各拠点がそれぞれ在庫を持つ。遠い地区を育てるには、そこへ食料を届ける経路が必要になる。

5. 共同生活の供給

各住人は所属する家と拠点を持つ。家の入口から拠点の入口までの経路コストが32以下なら供給対象。家の新規配置時は、到達可能な最も近い拠点を初期割当し、後から変更できる。

120 tickごとに、常住住人一人につき食料1個を要求する。在庫が足りる範囲で消費し、served／requestedを記録する。分配順は食事回ごとの巡回順とし、同じIDだけが常に優先されないようにする。

これは「拠点から各家まで一食ずつ描画する」処理を省いた、地区共同食の抽象化である。拠点までの配送は実物を運ぶ。拠点以降の食事アニメーションは消費結果の表現であり、二重に在庫を減らさない。

不足時も住人は死なず、泣かず、退去しない。拠点の食卓が小さくなり、新入居への余裕が下がる。供給できない住人は散歩・休憩などを続ける。プレイヤーは畑の場所、水、道、拠点、人口の受入れ方を変えて再試行できる。

6. 住人の行動

個体はID、既存の外見参照、家、拠点、好み2軸、行動、経路、所持品、予約、最近訪れた場所を持つ。性格に善悪や成績を付けない。

基本状態は idle → planning → moving → using → reacting → idle。配送は reserved → toSource → pickup → toHub → dropoff を別の仕事状態として持つ。

意思決定は5 tickごと、ID由来の位相で分散する。必須の受渡し・安全な移動完了を優先し、その後に配送担当、休憩、散歩、花や虫の観察を選ぶ。自律行動の行き先には距離、日陰、席の空き、好み、直近にしたことを用いる。同点の候補に乱数を使えるが、到達不能を抽選で選ばない。

自由行動の候補は、到達可能で経路コスト48以下の席・花・水辺・木の隣・拠点入口。各候補について以下の初期重みを使う。自然魅力Aは虫1、花／水辺0.8、木0.5、拠点／席0.1。近くの人Dは半径2内の人数÷3を0〜1に収め、日陰Sも0〜1とする。

score = 1 + 2*naturePreference*A + 2*socialPreference*D
        + 1.5*(1-socialPreference)*(1-D) + S
        - 0.06*pathCost - (直近2候補に含むなら1.5、他は0)
weight = max(0.05, score)

候補を安定ID順に並べ、weightの合計で正規化して一つを選ぶ。resident-choice / residentId / decisionOrdinal の専用乱数を使う。到着後は原則15 tick滞在し、対象消失や配送担当への切替は安全な区切りで処理する。候補がなければ近くの有効な地面で休み、エラーや永久待機にしない。座るときの見た目は座席アンカーへ合わせ、論理上は入口から出入りする。

場所の利用は定員を持つ。座席は一席一人、予約中の席を二重に使わない。満員なら他の候補へ向かう。無意味に並び続けさせない。キャラの見た目を変えるだけで性格差を表現したことにしない。

7. 人の集まりと場の変化

半径2セルに、休憩・観察中の住人2人以上が10 tickとどまった場合、短い共有反応の候補になる。同じ組合せは60 tickクールダウン。これは人口や通貨を直接増やさず、滞在履歴へ記録される。

ベンチや花、虫、食卓、道によって滞在が集まると、その場所は自然に「よく集まる場所」になる。S1では建物を勝手に増築しない。市場・祭り・職業の自動成立は後続。将来もプレイヤーの作品を無断で占有する建設をしない。

8. 編集・中断・やり直し

移動・配置・収納・撤去は無料。占有、入口、範囲、既存物、利用中の予約をコマンド単位で検証する。移動は撤去＋新規生成ではなく、同じentityIdの原子的変更にする。

利用中の施設を動かす場合は安全な区切りで行動を解き、持ち物を保ったまま再計画する。橋の撤去で住人を水面へ残さない。安全な岸へ一度だけ移す保護処理を使い、その例外を開発ログへ残す。家の収納も撤去と同じ検証を行う。入居中の家の撤去で収容先が不足する場合は拒否し、「家を動かす」へ誘導する。

取り消しは配置コマンドの逆操作であり、世界の時間・学習履歴・過去の抽選を巻き戻す機能ではない。実行時点で逆操作の条件が成立しない場合は、理由と安全な代替を示す。無限の完全巻き戻しは約束しない。
