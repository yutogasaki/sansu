# 要件レビューと改善の進め方

重要な仕事の実装前と成果物の確認に使う。正式な要件・判断・状態は既存の仕様、仕事詳細、証拠へ戻す。この文書やポータルに別の状態台帳を作らない。

## 実装前

対象の仕事、要件の版（commitと未commit入力hash）、目的、対象外、完了条件、制約を揃える。矛盾、抜け、反例、失敗条件を先に点検する。要件ごとに「充足／未充足／不明」と根拠を記録し、不明を合格にしない。指摘には発生条件、利用者への影響、根拠を添える。必須修正と任意提案を分け、採用・保留・不採用の理由を同じ仕事詳細に残す。

## 成果物の確認

同じ版の要件、成果物・画面、差分、成功／失敗／未実施の検証、前回指摘と対応を一緒に渡す。証拠には対象版・入力hash、日時、コマンド、期待／実結果、未確認範囲を残す。異なる版の画面や結果は混ぜず、版の不一致も不明として扱う。

再確認は変更箇所と影響範囲を中心に行う。2往復程度で費用と残課題を見直すが、未達の完了条件を緩める根拠にはしない。既存の検証matrix、停止条件、人の承認境界を優先する。

技術上の動作・表示・保存と、教材の正しさ、図や式の理解、学習価値は別々に判定する。AI同士の一致や自動テストを子どもの理解・再訪の実測に置き換えない。

## 失敗と改善

実際の失敗は入力、期待、実結果、対象版を既存の仕事と証拠に残す。再現性・重要性・維持費を見て、適した例だけ回帰テストや人の評価例へ移す。レビューで見落とした例も将来の評価候補にする。

手順を変えるときは同じ例で、見落とし、誤検知、人の修正時間、往復回数を比較する。未測定なら未測定とする。教訓には適用範囲、根拠、見直し・廃止条件を添える。AGENTSや恒久ルールには自動昇格させず、必要時に別の判断として扱う。

## ポータルからの依頼

「AI開発能力」「仕事・条件」「成果・評価」で仕事を選び、実装前または成果物レビューの準備ボタンを使う。既存の依頼ダイアログで要件・成果物・証拠の参照と版を補い、全文を確認してコピーする。ChatGPTへ自動送信しない。結果は選択した仕事の正本へ戻す。

導入、実使用、検証、採用、効果を分ける。この手順と準備機能の導入は、レビュー精度や開発速度の改善を証明しない。
