# 島制作を短く区切る進め方

2026-10-12。利用者の時間・トークン消費への指摘を受けた実行手順。目的は、育て方で島全体が変わる核心を早く判断できるようにすること。[制作方針](../product/island-construction-strategy.md)の完成条件は維持し、作業の単位を小さくする。現在の順番は[親タスク](../tasks/active/2026-09-27-living-fantasy-first-playable.md)、入口は[共有キュー](../../.agents/tasks/TASKS.md)。

## 1回の作業

1. 開始時に「目的ひとつ／成果物ひとつ／対象／検証／上限」を短く示す。既定は30分、追加エージェントなし。利用者が別の上限や並列作業を指定した場合はそれに従う。
2. 既存の正本・証拠・失敗ログを再利用する。必要な章だけ読み、大量の履歴・アセット・ログを一括で読み直さない。現在の問いに不要な調査や検査を追加しない。
3. 粗い本体結果を先に見せる。輪郭・高さ・通路・家と森のまとまりを判断してから、採用部分の細部へ進む。原本レンダーと本体実画面を区別する。
4. 失敗は最初の原因を保存し、原因に関係する最小修正・再検証を1回まで行う。それでも未解決なら止め、原因・次の一手を報告する。上限内で別案の連続試行を増やさない。
5. 成果物ができたら、残り時間で別の仕事を始めない。時間上限でも停止する。長いツール処理は残り時間を考慮した上限を設定し、停止・保存に必要な余裕を残す。中断した検証は未完として扱う。
6. 最後に「できたこと／検証結果と未解決／次の一手」を短く報告し、親タスクの現在地だけ更新する。次工程を自動で開始しない。

時間は開始時刻から測る。トークンの数値上限は利用者が明示した場合に記録し、利用可能な機能で管理する。取得できない使用量を推定値で断言しない。30分は完成保証でも消費トークン保証でもない。無制限の包括ゴールや自動継続を、確認なく再開しない。

## 検証を行うタイミング

- 文書整理だけなら `npm run docs:check` と変更文書の読合せ。アプリの全検証は増やさない。
- 試作・原因調査は、対象テストと必要な型・lint等を選ぶ。これは途中確認で、完成や配布の合格ではない。
- 採用して安定した候補で[検証表](../ai/verification_matrix.md)の必須チェックを実施する。時間内に収まらない全体検証は独立した作業として計画する。
- 同じ入力で合格済みの検査は、関連変更・失敗・未解決リスクがなければ繰り返さない。修正後は影響範囲から再検証する。
- 保存・学習・更新・配布の必須条件を省略しない。未確認のまま通常配布の切替や完成宣言をしない。途中状態のcommit/pushとリリース合格は分ける。

## 記録・素材・Git

現在地は親タスク1箇所、共有キューはその要約とリンクにする。完了履歴へ同じ長文を重ねず、必要な証拠へリンクする。完成率はテスト数やファイル数から算出せず、未達条件を示す。

証拠は判断に必要な実画面、初回失敗、対象結果、入力の識別情報に絞る。新しいラフごとに全ソース複製・巨大アーカイブ・大量の比較画像を作らない。正式な受入で必要な証拠は既存の検証契約に従う。

再生成可能な中間素材はローカル出力へ置き、採用した編集原本・実行アセット・必要な記録をGit対象に選ぶ。大きな追加があるときは合計サイズと生成可能性を確認する。既存の証拠・コミット履歴はこの整理を理由に削除・書換えしない。commit/push時は依頼対象の変更だけを含め、別作業を混ぜない。

## 今は先行させないこと

葉や小物の微調整、同じ局所造形の多数案、全rigの接触検査追加、全体テストの反復、内部ポータル整備。核心の実画面判断や安全な操作に必要になった時だけ、対象を絞って扱う。
