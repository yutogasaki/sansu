## Q-02 実装上の責務

| 領域 | 既存の接点 | 次期の責務 |
|---|---|---|

| ドメイン | `src/domain/islandLife/` | clock、growth、wallet、placement、residents、discoveryの純粋規則 |

| 証拠 | `docs/design/` と既存の検証matrix | 実対象のmanifest、contact sheet、個別判定と残件 |

描画モデルの位置と到達判定を別の定数で調整しない。同じmanifestから占有・利用点・観察点を渡す。異なる住人に固有の動作があっても、財布・clock・保存を住人ごとに分岐させない。

次期フラグ名は `VITE_ISLAND_FANTASY_ENABLED` を使用する。初期候補ではこのflagと `.life-world` の `data-life-visual-candidate="living-fantasy-garden-v2"` を実装済み。既定の公開起動で有効とは扱わない。v1全体の候補は `data-world-candidate`、規則集合は `living-fantasy-v1` として画面証拠へ記録する。初期候補はLife v20 / M4を使うため、v1の規則集合へ移行済みと記録しない。試験用clockや強制解放は別の検証専用入口に限定する。

OFFは既存未移行profileに現行表示を選ぶためのもの。移行済みprofileを古いwriterへ戻すスイッチとして使わない。移行済みprofileには互換readerか更新案内を返す。previewと本番のflag・DB名をmanifestへ明記する。

## Q-03 初期性能予算

以下は実機で確認する**目標と受入値**であり、現在達成しているという報告ではない。対象実機の機種・OS・ブラウザ・電源・温度・回線・cacheを測定に添える。機種未指定の「スマホで速い」を合格にしない。

| 項目 | 次期の基準 |
|---|---|
| 島の操作応答 | ポインタ操作から最初の見える応答P95 100ms以下 |
| 描画 | 配置30個・3住人・通水・精霊1件の60秒で、可視フレーム時間P95 33.3ms以下。収納1,000個の負荷も分離して検査。画質を下げても条件・動作は維持 |
| 起動 | キャッシュ済みの起動からDOMの学習・設定操作可能までP95 1秒以下、島の操作可能までP95 2.5秒以下 |
| 学習から帰島 | 島の操作可能までP95 1.5秒以下。初回の高解像度素材完了を必須にしない |
| 学習入力 | 現行の固定10問baseline以上のthroughput、通常問題間の追加tap 0、答え漏れ0。既存matrixの対象閾値も保持 |
| 次期世界の初回必須素材 | 圧縮転送量合計4MiB以内。既存app/教材と分けて報告。追加高解像度は遅延取得 |
| GPU初期設計予算 | phoneの世界texture約64MiB以内、visible draw calls 120以下、visible triangles 150k以下を制作予算。実測性能も別に判定 |
| 画像・モデル | 原則texture長辺1024px以下、必要な主役だけ2048px。mipmap・圧縮・fallbackを含め容量計測 |
| 復元計算 | 長い履歴をWorkerで処理し、メインthreadの50ms超の連続占有を残さない。操作可能DOMを先に出す |
| 背景 | 描画ループ・音を止める。戻っても学習・clock・取引を二重適用しない |

起動・帰島は各10回以上でP50/P95を示し、coldとwarm、service worker更新直後を分ける。描画負荷のfixture検査と、実学習で取得した品による一周を両方行う。PCのemulationだけでiPhoneの起動・電力負荷を認定しない。電池消費は現行と同条件の10分観察で比較し、熱・描画劣化を記録する。

低性能端末では先に影解像度・葉の量・反射・背景生物・粒子を減らす。住人の接点、顔、通路、現象の識別、文字・操作を削らない。自動画質変更は所有・発見条件を変更しない。

## Q-04 美術・理解・runtimeの独立判定

**美術:** [.agentsの美術基準](../../../.agents/skills/sansu-art-direction-loop/references/value-gate.md)の6軸を使う。入ってみたさ、相棒への愛着、素材、構図と奥行き、焦点となる色、出来事と結果を各10点で記録する。原則52/60以上かつ各8点以上、承認済みbenchmarkを下回らない。採点対象が生成画像・mock・runtimeのどれかを明記する。候補絵の採点をruntimeへ転記しない。

**無説明の理解と安心:** 5人の独立した観察で、4人以上が同じ主な動作と結果を言え、4人以上が続けたいと答えること。怖い・痛い・閉じ込めた等の妥当な解釈が1件でも出たら修正して再確認する。相棒と水／花のように島の動作に合う問いを使い、旧の大きな生物の救出を前提とした問いを機械的に適用しない。回答は本人の言葉を記録し、作者が説明して誘導した結果を無説明と数えない。

**runtime:** 画面・学習・入力・保存・移行・更新・性能を独立してPASS/HOLD/FAILで報告する。機能テストが通っても美術が弱ければ未完成、絵がよくても保存や理解が不十分なら配信保留。対象の子どもの観察が未実施なら、作者の画面確認をその代わりにしない。

5人の形成的評価は全利用者の好みや学習効果を推定する統計調査ではない。実家庭の利用では初回と数日後に、選んだ物を覚えているか、自分で置き換えたいか、追加の説明なしで同じ学習へ戻れるかを確認する。点数・見た時間だけから意欲や能力を断定しない。

## Q-06 必須コマンドと証拠

実装後は[検証matrix](../../ai/verification_matrix.md)に従い、変更範囲に対応するdomain検査・UI journey・保存・PWAを行う。共通の基礎は `npm run docs:check`、`npm run lint`、`npm run typecheck`、`npm run test:run`、`npm run build`。release時は `npm run verify:release` に加え、**島有効かつ次期flag有効の対象**でT-04〜24とT-26を必要な統合journeyへまとめて確認する。T-01〜03の表現確認と三ゲートも別途必要とする。

classic Exploreのsmokeや旧契約のE2Eを、次期島の合格として代用しない。既存ハーネスのexpectationを変えるときは、仕様差分を記し、検査を削って緑にしない。新しいT番号は受入要件であり、同名のテストスクリプトが既に存在するという意味ではない。

証拠manifestに実app target、build revision、appとQAのhash、flag、DB namespace、rules版、visual candidate、asset manifest、cache／SW更新状態、viewport、機種、日付、source（実獲得／fixture／故障注入）を持つ。

contact sheetは起動→通常の庭→材料選択→配置→住人利用→発見前／中／後→おもいで→家→学習入力→帰島を同じ候補で並べる。昼と夕ぐれ、phoneとtabletも含む。古い画風が意図せず混在した場合は未完成とする。旧snapshotの再演は旧版表示であることを明記し、現在の導線の混在と区別する。

## Q-07 採否と変更管理

未実施はHOLD、明確な不成立はFAILとする。美術・理解・runtimeの三つを個別に示し、実機・利用者が未確認のときに総合PASSを出さない。今回の仕様書検証はリンク・構成・相互整合の検証であり、この三ゲートを通したことにはしない。

実装中に変更したくなったら、担当章に理由、変える契約、旧データへの影響、追加受入を記録してrules版を更新する。価格・成長式・発見条件は過去へ適用しない。美術だけの修正でも接点・遮蔽・視点が変われば関係する操作・可視性の検査を再実行する。

v1を小さくする場合も、正確な学習接続、本人の選択、暮らし、通常の庭での不思議、記録、保存移行を分断しない。削る順序は後続機能→装飾差分→環境演出の量。信頼・入力・owner分離・旧所有物の保持を削って日程を合わせない。

## Q-08 今回の仕様策定の完了条件

入口と8章が揃い、現行文書に対象を限定した次期参照があり、担当する正本が明確であること。価格・成長・発見・来訪・所有・画面・異常系・保存・移行・後続範囲・受入が辿れること。`docs:check` と文書portalの生成・整合検査を行う。

コード・DB・公開版を変更していない仕様策定では、変更のないアプリ入力に対するbuild・全E2Eをこの文書のPASS根拠として実行しない。実装後の三ゲート、実機、子どもの観察は次段階の作業として正確に残す。
