# 06. データ・保存・現行への接続

## 1. 確認できたこと／未確認のこと

元ZIPの `04_OPTIONAL_CURRENT_CONTEXT.md` は、React／TypeScript、Three.js、ブラウザ内保存、PWA、算数と英語、プロフィール別学習、ぽこもこ・うさぎ・カワウソを現状の参考として記載している。これは**概要の記述**であって、今回リポジトリや最新配信版を検査した結果ではない。

実際のバージョン、ディレクトリ、保存キー、学習イベント、既存のキャラ品質、テスト構成は未確認。技術を全面変更する理由にはせず、実装AIが現物を確認して対応させる。

## 2. 責務の分離

```text
既存学習システム ─ durable completion events ─ 学習アダプター
                                            │
                                     進捗台帳・解放権利
                                            │
UI入力 ─ コマンド ─ シミュレーションコア ─ 状態・出来事 ─ 描画
                         │
                  保存／読込／再現テスト
```

シミュレーションコアはReact、Three.js、DOM、音、実時計、ネットワークを知らない。乱数源・地形・設定を入力として持ち、状態遷移をテストできるものにする。描画側が人口・在庫・抽選を増減させない。

## 3. 必須データ

| 集約 | 主なフィールド | 注意 |
|---|---|---|
| ProfileProgress | profileId、発行イベントID、発行量、使用量、権利、目当ての道具 | 世界の取り消しから独立 |
| WorldState | worldId、profileId、schemaVersion、engineVersion、seed、tick、revision | 実時計でtickを進めない |
| Chunk | chunkId、座標、開拓状態、セル、地形生成バージョン | 世界座標、隣接境界を維持 |
| Entity | id、definitionId、位置、入口、成長・在庫等 | 動かしてもIDと所有が変わらない |
| Resident | id、外見、家、拠点、好み、行動、経路、荷物 | 同じ住人を別インスタンスとして複製しない |
| Job／Reservation | source、destination、担当、数量、状態、作成tick | 一つの食料を二重予約しない |
| DistrictMetrics | 直近240 tickの要求／供給／配送、通行、滞在 | 表示用のアルバムとは別 |
| RandomState | 系統・対象の評価回数、seed、未処理候補 | 保存・再起動で引き直さない |
| Observation | eventId、実際のtick、対象、場所、観測条件 | 因果や理解を自動断定しない |

`contracts/model.ts` は境界の型案。既存コードに同じ名前があることを意味しない。実装に必要な補助フィールドは追加できるが、不変条件を弱めない。

## 4. コマンドとイベント

入力コマンドは `commandId / profileId / worldId / expectedRevision / payload` を持つ。配置、移動、収納、道・水路の作成、拡張、入居受入れ、道具取得、学習イベント受理を扱う。道のブラシ全体など一つの意図は一つのコマンドとして検証する。

同じcommandIdは一度だけ適用する。revision不一致は最新状態へ同期して再評価し、勝手に二重実行しない。保存領域の複数画面から同時に書くことを許さず、S1はプロフィール単位の単一書込み者とする。別タブは読取専用または引継ぎを要求する。

ドメインイベントは状態遷移から作る。`FoodHarvested`、`FoodTransferred`、`MealServed`、`VisitorArrived`、`SettlementOffered`、`ResidentAdmitted`、`ChunkOpened`、`CapabilityUnlocked`など。イベントの再描画で状態遷移を再実行しない。

## 5. 学習イベントの耐障害性

学習記録の確定と、ゲーム側の報酬反映の間に終了が起こり得る。学習側の永続完了記録／outboxを正とし、ゲーム側は同じ完了IDを何度受けても一度だけ単位を付ける。再起動時は未反映の確定イベントを再読込する。

学習とゲームが別保存方式なら、両方を同時に書けると仮定しない。まず学習側が確定し、後からゲームへ冪等に反映する。学習の確定前にゲームだけへ単位を発行しない。既存基盤に再取得可能な完了履歴がなければ、その接続は「未実装」として止め、疑似採点で埋めない。

## 6. 保存

保存はschemaVersionとengineVersion、設定バージョン、チェックサムを持つ。世界は定期的に、ユーザー操作と学習反映・解放・入居の確定時は速やかに保存する。visibility変更時だけの保存に依存しない。

更新中の終了に備え、直前の有効スナップショットを残す。完全な新スナップショットが検証できるまでは古いものを消さない。複数の保存領域がある場合は、トランザクションまたはコミット指標で整合を保つ。

読込時は数値の有限性、在庫上限、ID参照、プロフィール一致、権利台帳、予約整合を検査する。破損データを新規世界で黙って上書きしない。復旧可能な版と、保護者向けの書き出しを提示する。

ブラウザ内保存だけを唯一の永久保管場所と扱わない。保護者用にプロフィール別の書き出し／検証付き復元を用意する。外部への送信・公開は初期仕様に含めない。

## 7. オフラインと時刻

必要なアプリ本体・既存素材・問題データが取得済みである状態で、オフライン起動・学習・世界操作・保存ができることを確認する。未取得の追加素材まで通信なしで使えると表示しない。

世界は実時間の経過を使わない。7日・30日の休止や時計の巻戻しでも、住人・食料・権利は不在分で変わらない。学習の復習日時は既存学習基盤に委ね、世界の幸運率と混ぜない。

## 8. 旧世界と移行

新エンジンは別namespaceとfeature flagで導入する。旧保存形式・旧通貨・旧作品をそのまま破壊的に読み替えない。元データ、ハッシュ、バージョンを残したコピーで検証する。

学習履歴は既存の正本を維持する。既存のキャラ素材と対応IDはマッピングし、美術を勝手に置換しない。旧世界は旧版表示またはアーカイブとして保護する。新モデルへ表現できない家具や配置を黙って削除しない。

旧通貨→新学習単位の比率は未決。1対1や総額リセットを実装しない。必要なら旧権利を別欄で保持し、所有物を遊べる形と、進捗への変換を別問題として報告する。

本仕様作成時に現行データの変換は実施していない。本番移行は変換テストとユーザーの明示的な実行指示を得て行う。

## 9. 性能・拡張

S1は全チャンクを同じtickで更新する。描画は画面内中心にしてよい。安定ID、チャンク境界、能力定義、状態、演出を分け、地形変更時だけ経路再計算範囲を更新する。

将来試験は24／96人、8／24チャンク。これを通ったと主張するには対象端末、設定、時間、FPS／tick処理時間、メモリ、保存サイズを記録する。ここでは実測していない。

実行時の生成AI、クラウド推論、外部課金サービスはコアに不要。診断ログはまずローカルのみ。子どもの名前・学習内容・行動を無断で外部分析サービスへ送らない。

## 2026-09-16：保存後の受渡し表示

`DomainEvent.FoodTransferred` は各受取り／納品で一度発行し、送り手・受け手のIDとそのtickの両端座標を `transfer` に含める。集約した配送量を重ねて再発行しない。イベント追加は物量・経路・抽選・消費条件を変更しない。

画面側は2倍速の各tickのイベントを集め、snapshot保存に成功した後だけ世界と一緒に表示する。直近6tick・最大24件のメモリ内表示であり、WorldStateやDBのschemaへ追加しない。編集・復元・再読込では表示を引き継がず、過去の受渡しを再発生させない。保存エラー時には未確定の出来事を公開しない。
