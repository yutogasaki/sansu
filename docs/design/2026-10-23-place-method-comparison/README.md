## 何を成立させるか

同じ取得土地・所有物・成熟から、普通のゲーム操作で異なる場所を作れること。見た目、家や家具の接地、住人の実利用、Undo/Redo、保存再開をそれぞれ確認する。最終目標は[島の構築方針](../../product/island-construction-strategy.md#ゲーム中の自由編集と完成の条件)のまま。一角だけの成功や固定の完成島の表示で置き換えない。

今回の比較では、本体の画面・command・住人・共有床を使うローカル専用buildを作った。`src/` と `public/` はこの作業では変更せず、このフォルダのVite変換で候補を差し替える。表示・クリック・家具支持・経路は方式ごとの同じ床を参照する。所有権や住人保護を外して成功扱いにしない。

## 現時点で分かったこと

1. **補間を丸くするだけでは足りない。** A/B/C/D/F/G/Hを比較したが、台・壁・細い段差の反復が残った。土地を96区画へ広げた比較でも、広さだけで参考美術の場所構成は生まれなかった。
2. **形を変えると、使える床も変わる。** 高台をつなぐDには一段操作で周囲が1m以上動く反例があり、棄却。Fは一段の変化を18cm以内に保てた。曲線格子Hはその編集と配置を維持したが、美術は未達。
3. **上面と坂を分けて考える必要がある。** 全区画の中央を平らにするFは坂を段々にする。線形の坂へ替えると段壁は減る一方、穴の隣には家具を置けなくなる反例もあった。置ける面の広さを作り、花・ベンチを通常移動する対照を通した。
4. **拡張と接地に隠れた不整合があった。** 土地を買うだけで既存の基面や外縁補間が変わる。基面固定の候補は初期範囲の変化を消したが、外側通路に副作用が残る。実モデルの接地と、半径による簡易支持判定も一致しない。
5. **静止中の滑らかさでは編集性能を判断できない。** 新規の編集候補を全計算する際に、実ブラウザで約1.7〜1.8秒の停止を確認。同じ操作の再試行はcacheにより速くなる。二重compile削減だけでは停止を解消できなかった。1編集あたり約63万回の試験設定読取りを起動時へまとめ、同じv15の実UI対照で地形計算1600.1→432.6ms、最大描画間隔1666.7→500.4msへ短縮した。それでも操作性能は未達。

この大きな短縮は、比較実装が追加した試験設定の反復読取りを除いた効果が中心である。**製品そのものを1.7秒から0.4秒へ改善した、という結果ではない。** 製品sourceは変更せず、最終試験版にも約0.4秒の停止が残る。

## 次の投資先

参考のnative-05が持つ、大小の場所・上面・登り口・岸・水の抜けを一組として作る方法が不足している。一段の境界を磨く回数を増やしても、全体構成の代わりにはならない。次は**上面の輪郭と入口幅を持つ「場所」を一回の編集単位にする仮説**を最初に試す。同じ所有物・生成規則で高い岬の庭と低い入り江の庭を作り、幅変更・入口閉塞・Undo・新しい住人利用・保存再開を通せるかで判断する。これは未実装の次候補であり、現在の方式では不可能という証明ではない。手作業の細かな彫刻を遊びの必須条件にせず、編集前の島も成立させる。全島を再計算しない処理と実モデルの支持面を合わせて扱い、小物の増量や色変更を先行させない。
