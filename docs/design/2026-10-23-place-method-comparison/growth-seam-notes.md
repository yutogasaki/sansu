# 拡張で旧端の足元が変わる原因と、隣接一列の引継ぎ

2026-10-23 JST。候補 `new-adjacent-row-inheritance-v1`。通常の土地取得トランザクションだけに作用する比較用transform。製品sourceは変更していない。`growthTrial=inherit` で有効、A/F/Hの選択とは独立。

## 確認した原因

`editableTerrainWorld.ts` の `rawHeight` は、**現在の**取得範囲でサンプル座標をclampする。南端z=4の時、z=4〜4.5はz4の編集高さが外へ延長される。南に取得してz5が内部になると、同じ旧足元はz4→未編集z5=0の補間へ変わる。保存した旧セル値が全て同じでも、その外半分が斜面になる。

独立担当が実UI保存33を入力に、通常のexpandを使って西→東→南と東→西→南を診断した。基準Aのベンチ `(2,4)` は中心高0.36mのまま、旧面からの追加傾斜が約0.0796m→0.2042mとなり、支持不可へ変わった。F2でも約0.174125mとなる。最悪点は `(2.46,4.46)`。初期30中心の値とterrain履歴が変わっていないことだけでは、この破壊を検出できなかった。

さらに以下の境界依存があるため、最初のclamp問題だけ直しても全形状が不変とは限らない。

- F2は現在の外縁でA補間に戻す。旧端が内部になると、同じ旧セル内でも補間の形が変わる。
- 共通foundationは現在の桟橋位置を `maxX−1, depth−1` で求める。拡張で旧pinが外れ、新pinが加わる。
- baseTerrainHeightAtは初回取得後に拡張向け基面を有効化する。初期の整数中心は平らでも、境界の外半分は差が出る。
- sceneLayoutの桟橋位置も現在boundsから求まる。Hの固定座標写像はこれらの高さ・足場変更の解決にはならない。

基準証拠は独立担当の `/private/tmp/sansu-growth-continuity-A.json` と `...-F.json`。この作業では同じ基準試験を重複実行せず、結果とsourceを照合した。基準Aの花 `(2,3)` は拡張前から支持不可なので、今回の新規破壊と分けている。

## 最小の修正

取得成功候補のstateで、**新しく取得されたセルのうち、旧範囲に直接接する一列だけ**へ、旧境界の整数offsetを引き継ぐ。旧端の外半分を、突然0へ傾けずに同じ高さで受けられるようにする。旧セルは一切上書きしない。明示的な0を含む既存heightキーも上書きしない。取得していない未来のセル、二列目以降には値を書かない。

これは描画時に繰り返す補正ではない。土地取得時の新セル初期値として一度だけ保存する。後から新しい列を編集した値は独立した入力として扱い、所有物の移動や次の描画でコピーし直さない。初期島全体を固定する方式ではなく、任意の後続districtでも旧境界と今回の新セルの関係から計算する。

通常のexpand内で土地を更新した直後、soil同期とbridge再配置より前へ初期化を入れる。その後、applyIntentの成功を返す直前に、拡張前に支持成立していた既存ownerの足元が今も成立するかを検査する。複数セルのlandmarkは現行terrain-editと同じoccupiedCellsを使う。支持閾値は緩めない。

失敗時はapplyIntentが内部で作ったcloneに対してthrowする。元のland、通貨、applied履歴を途中状態へ書き戻さない。既存のunsupported入力を修復できたとは呼ばず、新しい破壊のみを拒否する。これが単に全ての拡張を止める案にならないことは、独立担当の通常expand試験で判断する。

## 保存とUndoの意味

保存形式はterrain version 1の整数heightsのまま。引継ぎ値は範囲−4〜12を保つ。新しい特殊base layerや非表示のshape状態を導入しない。

既存terrainのundo/redo配列は変更しない。引継ぎは「土地取得で作った初期値」であり、1回の地形操作としてundo配列には追加しない。そのため拡張後のterrain Undoは、以前の編集を戻す一方で新しい列の初期値を残す。これは意図した限定仕様であり、拡張自体のUndoを提供したという意味ではない。新列への通常編集は通常通りUndo/Redoできる。履歴の現在状態と新しい支持が両立しないUndoは、既存の安全判定で拒否され得る。

## 明示して残す限界

一列だけの引継ぎなので、負入力で旧海岸へ開けた入口が、新しい二列目以降の0によって海と切り離される可能性がある。今回の一列というscopeを、海への開口が永続する保証に読み替えない。正の高い台から新しい二列目へ急斜面ができる可能性もある。

Fの境界blend、旧pier保護の解除、基面の初回変更は残る。引継ぎ後にowner支持が壊れる反例は、原子的に拒否する。床の全頂点不変、全ルート維持、移動中actorやoccupied galleryのsnapshot保護まではこの追加guardの契約に含めていない。

## 検証の分担

新規 `growth-seam.ts` と `growth-seam-transform.mjs` のESLintはexit 0。transformの文字列差替えは一箇所一致を要求し、元source不一致なら明示エラー。ブラウザ条件はqueryのみ、Nodeの独立試験は `growthSeamCommandTransform(source,{alwaysInherit:true})` を使う。

独立担当の両順序の通常取得がA/Fで完走した。南取得後のベンチ追加傾斜はA 0.0796m、F 0.0645625mとなり、支持成立。旧整数中心・旧heights・Undo/Redoを保持し、Fのgarden利用と両actorのsyncも維持した。証拠は `/private/tmp/sansu-growth-seam-A.json` と `...-F.json`。

引継ぎ呼出だけを外した独立fault injectionでは、既知の南ベンチ破損を残ったguardが拒否し、元のstate全体・残高・appliedが不変だった。これはguardの拒否動作の証拠であり、通常候補を故意に壊した結果と分ける。

ただしFは旧岸辺のdry喪失と半セル経路喪失が残る。西→東→南で各3/21/11点、東→西→南で8/10/11点がwetへ変わり、`0,3.5` / `5,2.5` の既存到達点が失われる。Aでは同診断のdry/経路喪失は0。したがって取得全体の合格ではない。別候補 `growth-fixed-*` で境界依存の補間切替を取り除いて診断する。rootがVite本体への接続とUIを担当する。
