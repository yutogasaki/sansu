## 目標を先に固定する

**子どもが普段のゲーム操作で自分の島を変え、美しい景色と住人の暮らしが一緒に変わり、その島を明日も続けられること。**

自由に変えられること、配置が変わっても美しいこと、住人が実際に使えること、所有と成長を保って保存できること、愛着と学びにつながることを別々に判定する。調査先の見た目に似たことだけで達成としない。製品の正本は[島制作戦略](../../product/island-construction-strategy.md)。三つの全島配置・拡張・学習往復などの最終条件を、この調査で小さくしない。

最初の成立確認は、**同じ土地・所有物から、通常操作で意味の異なる二つ以上の場所を作り、住人が実際に使い、戻せて、再読込後も続くこと**。この最小実験と、全島の美術合格は別である。

## 監査結論

不足は参考作品の数だけではなかった。既存調査は形の仮説をかなり絞っているが、**観察した仕組みを、制作コストと遊びの成立を含めた方式選択へ変換する証拠が不足**していた。

今回の追加で優先順位を変える。丸みの調整を増やす前に、同じ編集状態から「見える形・支える床・通路・利用地点」を一貫して作れるかを比較する。連続地表と造形済み部品の優劣は未確定。両方に同じ利用判定を適用する。部品方式を選ぶ場合も、見た目だけのキットではなく、入口・支持・利用地点まで含めた制作単位を試す。

## 追加の一次資料から得たこと

### Townscaper：少数の万能部品で済むとは限らない

作者は2019-10-29時点で[378モジュール](https://x.com/OskSta/status/1189109278361165825)と説明し、同日の投稿で[ランダムな形を作って不足ケースを補う制作](https://x.com/OskSta/status/1189122653048717312)、[Marching Cubes由来の候補とWFCによる接続解決](https://x.com/OskSta/status/1189154686210891777)を述べている。2020-09-14には[操作する格子と四角形のdual gridの役割](https://x.com/OskSta/status/1305467415627812865)も説明している。

採る知見は「接続条件を設計し、実際の編集で不足ケースを発見する」こと。378をSansuの必要モデル数・完成時の総数・必須最低数にはしない。四隅の組合せ数もそのまま必要素材数ではない。WFCの影響範囲は、今回の独立した四隅補間の4区画に限定できない。

### Tiny Glade：美しい反応と編集履歴は両方作り込む

作者の[2022-05-28 Undo/Redoスレッド](https://x.com/anastasiaopara/status/1530473522224582656)は、地形や道に応じて変わる形と、壁の分割などを戻す操作の複雑さを説明する。[2024-05-30の開発者インタビュー](https://80.lv/articles/exclusive-tiny-glade-developers-discuss-bevy-proceduralism-publishers-cozy-games)では、要素別の生成器を組み合わせ、操作感も反復している。

[公式説明](https://store.steampowered.com/app/2198150/Tiny_Glade/)には道に反応する建物や羊もある。したがって「生き物の挙動がない」とは扱わない。一方、Sansuの所有・成熟・学習・継続を含む生活の証明にはならない。今回は実ゲームを操作していない。

### Little Habitats：「50プロンプト」は制作手法の答えではない

作者の[2026-09-27投稿](https://x.com/DannyLimanseta/status/2104122809484214376)は、Townscaperの技術調査を先に行い、100以上の素材と50回以上のプロンプトで制作したという本人説明。[同日の初期指示の紹介](https://x.com/DannyLimanseta/status/2104126569409347705)は記憶からの再構成で、全履歴ではない。

これは「最初に方式を研究する」根拠になるが、50回繰り返せば同品質になる、必要工数が分かった、同じ内部アルゴリズムだった、とはいえない。内部コードは未取得。H2は独立仮説のままである。

### Foundation：形と利用をつなぐ部品の契約

[公式Building Asset Processor資料](https://polymorph.games/foundation/modding/building-asset-processor)（最終更新2025-06-27）は、部品・接続位置だけでなく入口と順序付き経路をモデル側に定義する方法を示す。複数経路の共有終点は入口Aから入りBへ出る動作にも関わる。[建築段階の資料](https://polymorph.games/foundation/modding/construction-steps)（2021-10-21）は段階ごとの見た目を用意する。

この公開された制作契約が、今回新しく追加した重要な参照。Sansuへの推論は、**岸・段・建物の外形だけでなく、支持面・入口・利用地点を同じ制作単位で扱う**こと。ただしFoundationの経済・管理規則やエンジンを持ち込む提案ではない。実ゲームの操作と内部実装の検証はしていない。[公式wikiのBuildings](https://wiki.polymorph.games/foundation/Buildings)にも、自由追加した装飾が機能・収容力を増やすとは限らない説明があり、見た目と機能を混同できない。

## 制作戦略への反映

今はエンジン変更や大量の素材制作へ進む根拠が足りない。[既存のA/B計画](../2026-10-22-making-methods/README.md)を維持し、最初の比較に**場所の実利用**を必ず含める。A＝連続地表＋設計した断面、B＝造形済みの岸・段の接続。入口・支持・利用地点の契約は両方へ適用する。共通契約とは、異なる形状へ同じ経路結果を強制することではない。

比較の入力は、同じ土地、同じ家1軒・木6本・住人1体、同じ所有・成熟、同じ光・尺度・カメラ。設定ファイルや実験用コンソールではなく、最終的には通常の編集操作から変える。調査用の独立試作で通っても、通常ゲームへ接続するまで「ゲーム中に自在に扱える」とは呼ばない。

| 順序 | 試すこと | 採否を決める証拠 |
| --- | --- | --- |
| 1：最も重要な未検証点 | 同じ所有物で、合法な二配置を作り、家前→木陰→岸を住人が実際に使う。高さ差と入口向きも含める | 実形状からの支持/到達判定と行動記録が一致。床を偽装せず、住人の移動中に編集しても貫通・宙浮き・架空利用を生まない。不成立は安全に扱う |
| 2：操作の継続性 | A→B→Undo/Redo→保存/再読込。別の操作順で同じ最終状態も作る | 所有ID・成熟・位置・利用可能地点・形状/材質の一致。揺れなど時間依存の演出は条件を揃えて比較 |
| 3：美術と一般化 | 二配置とも昼の全景/近景で採用参考と比較。事前に固定した未調整配置・穴・対角・高低差・混在材質を追加 | 特定座標への手直しなしで、厚み・大中小・密度/余白・接地が維持。両方式とも基準未達なら低い方から勝者を選ばない |
| 4：増やす費用 | 同じ追加ケースをA/Bへ導入し、作業時間・新規部品・特殊分岐・未対応件数を記録 | 初期部品数でなく、次の一ケースを支える費用を比較。WFCなど全体波及も別測定 |
| 5：製品へ接続 | 選んだ方式で三つの全島、16/32軒、学習往復、保存/offline、対象端末を検証 | 最終仕様の全条件。子どもの無説明理解・再訪は実利用者の証拠で判定 |

1〜3の成立確認は一つの比較成果物にまとめる。機械検査だけを先に増やして美術を後回しにしない。採用前に、一配置ではなく配置差を見せる。使用不可地点を意図的に置かせる提案は、製品の合法配置ルールを破らない診断環境に限る。
