# 受入条件と相談結果

## 1 設計相談の範囲

2026-10-20の [チャッピーとの相談](https://chatgpt.com/c/6ad53525-5898-83e8-b607-becbc3ff6e11) を、現行コードとの照合を含めて具体化した。過去の画像レビューの点数や「GO」を、本案のruntime・公開の合格へ流用しない。

今回は設計の構造・操作・状態・候補寸法・受入条件までを作る。アプリのコード、通常配布flag、保存形式を変更する工程は含まない。画面単位の仕様は [全画面31節](screens.md) にある。

## 2 相談で修正した判断

| 論点 | 最初の案・懸念 | 本案の判断 |
| --- | --- | --- |
| 拡縮 | 全景／近景の固定二択 | ユーザーの方針を優先し、魅力的な既定＋連続拡縮＋全景復帰 |
| camera範囲 | 1〜2.8の新しい制限 | 現行の内部1〜4を維持。初期構図のみ再設計 |
| 大島の初期表示 | 全島fit×1.5では住人が小さい | 家の実座標へ寄せ、実物投影から範囲内で初期値を決める |
| ドラッグ | 全てpanにすると住人運搬が消える | 現行carry、二本指回転、wheel、7px閾値を維持 |
| 二本指へ移行 | ghostも消える可能性 | タップ候補とcarryだけ取消、ghostと所有を保持 |
| 小画面の高さ | 固定寸法の合計がsafe areaを超える | 実viewport・実navで計算、min高＋内部scroll |
| 品物説明 | 選ぶたび詳細を必須にすると手間が増える | 1tap仮置きを維持。必要な品だけ任意説明 |
| 情報button | タイル上の小さな右下hitは押し間違い | 主buttonと重ならない兄弟button、48px、可視「くわしく」 |
| メニュー | 新しい大カード化 | 実住人＋既存6入口を継承し、絵・文字・押し反応を磨く |
| パネル | 非modalと既存modalを見た目だけで統一 | 意味は維持し、一枚の主パネル・明確な背景操作・focus復帰を定義 |
| 未処理の一括処理 | 贈り物の通知と呼ぶと実commandと違う | つぼみと船の実状態を示し、一括と個別を同じ状態へ接続 |
| オフライン | 接続なしを保存失敗と混同 | local first。端末内保存の可否と通信を分離 |
| 共通化 | 全画面同じ白い格子になる | 操作部品を共有し、島・品物・住人・本・写真・学習の構図を分ける |
| 模様替え | 新しい保存buttonを足す | 現行の即時反映を維持 |
| 画像 | 全品新規生成・新規viewer | 現行の実物・identityを使い、実表示とcacheを共通化 |

第3ラウンドの最終要約に対し、チャッピーは「構造・状態・操作の基本方針に重大な矛盾は見当たらず、4点の追記で設計具体化を閉じてよい」と回答した。4点は全景の座標基準、非modal時のキーボード遮断、carryから二本指への取消完了、保存結果不明時の二重実行防止。本案へ反映済み。これはチャッピーへ提示した設計要約の整合性評価で、5ファイル全文や最新runtimeの独立監査ではない。全文の相互参照と現行契約との読合せは作成側で行う。

最終要約後に具体化した運搬のDOM代替操作は、現行のpick・drop・利用可否を共有する任意入力として記述した。この補足自体をチャッピーの承認済みと扱わず、実装時に同じゲーム規則へ接続できることを検証する。

設計として決めた項目は画面構造、入口、候補寸法、主役の大きさ、操作順、戻り先、状態表示、使用素材、gestureと保存の境界、受入条件。今後の実測は次の3群に分ける。

1. 初期構図と倍率、成熟した島での視認性、pinch・carryの実機操作。
2. 実model・絵・材質・余白・光・反応が作る実画面の魅力と全画面の連続性。
3. 子どもの無説明操作、安全、自発的な再操作と別日の再訪。

runtime・保存の実装検証も別に必須であり、この3群だけで機能の合格を保証しない。

## 3 採用しない案

- 初回全景を毎回見せてから強制zoomすること。
- 住人を運ぶgestureや二本指回転を、操作整理だけを理由に撤去すること。
- 文字とhitを小さくしてメニューを小さく見せること。
- 全商品への新しい詳細必須画面、学習前の毎回の設定、毎問の次へ、追加の報酬受取。
- 画面の全面に縫い目・水玉・粒子・色付きカードを敷くこと。
- 住人・成熟物・記念品を偽って増やし、にぎわった印象だけ作ること。
- 不足や未解放で悲しい顔を出し、学習へ誘導すること。
- 保存中の更新・強制reload、失敗時の黙った上書き、別本人のデータの混用。

## 5 端末とアクセシビリティ

基準は390×844。追加で320×568、360×640、768×1024、1024×768、568×320を確認する。safe areaあり／なし、browserとPWA、文字200%、長い名前、日本語変換・soft keyboardを含める。

各代表画面は通常motion、動き少なめ、音OFFを確認。全状態×全端末の形式的な総当たりより、同じ所有状態の主旅程と境界状態を組み合わせ、未実施を明記する。短い横画面で世界を160px見せるだけでは操作性の合格にしない。

主要hit48px、本文のcontrast、focus可視、Escの一重処理、Tab順、スクリーンリーダーの名前と状態を確認。手紙・英語音声・UI音の干渉、退出停止、無音でも理解できる状態を確認する。

## 6 合格を分ける

| 判定 | 確認すること | 代わりに使えない証拠 |
| --- | --- | --- |
| 美術と魅力 | 現行の採用benchmarkと同じcropで、主役・形・材質・接地・余白・押し反応を実画面／動画で比較 | token、角丸、画像サイズ、ソース画像だけ |
| 理解と安全 | 説明なしで入口を見つけ、配置・取消・拡縮・帰還を行える。失敗時に責められたと感じない | 作者と実装者の理解、自動テスト、チャッピーの設計評価 |
| runtime | 保存・所有・成長・入力・SRS・速度・PWA・本人切替が保たれる | 美しいモック、文書の完成、過去の別版のテスト |
| 再訪 | 子どもが自分でまなぶを選び、次の日も島へ戻るか | 初回の好評、タップ完了、学習テストの合格 |

美術・理解／安全・runtimeを平均点で相殺しない。数値評価する場合はcandidate ID、viewport、証拠種別、日時と信頼度を付ける。今回の設計協議はこのいずれの実測合格も主張しない。

実装後は起動→島→menu→品物→配置→住人→目標→家→学習→帰島→記録／設定をcontact sheetにし、app対象、revision、delivery flag、candidate、cache／更新状態を添える。意図したモード差と、旧新の不整合を区別する。

## 7 実装へ渡す順番

1. [本案](README.md) と現行正本の差分をUI・camera・遷移・保存別に明示し、必要な正本を先に同期する。全体の一括書換えをしない。
2. 共通token・hit・見出し／閉じる・選択状態・sheet内scrollの部品を対象画面で固める。寸法だけで美術採用としない。
3. 同じ所有状態で「島＋menu」「品物＋配置」「学習＋帰島」の実画面を先に比較する。主役のサイズと操作を同時に確認。
4. 合った操作部品を家・住人・目標・図鑑・写真・記録・設定へ適用し、各画面固有の構図を維持する。
5. 変更別の [検証matrix](../../ai/verification_matrix.md) を実装単位で実行する。routing・保存・PWA・学習の追加検証を省略しない。
6. 独立した無説明操作と再訪を別に観察し、公開判断は人の明示承認で行う。

## 8 文書だけの検証

本案の作成で行う検証は文書のリンク・構造と正本・コードとの読合せ、`npm run docs:check`。アプリの動作を変えていないためlint・unit・build・E2Eを新しく実行した証拠とはしない。結果と対象hashはこの節へ記録する。

実行日時・コマンド・実結果・5文書とchecker等の入力SHA256は [検証記録](verification.json) に保存する。リンク、表の列数、コード枠の閉じ、31節の存在も対象にする。

環境の `nvm use` はnvmが未導入のため実行できなかった。最初の `npm run docs:check` は既定Node v24.18.0でPASSしたが、最終検証はインストール済みfnmのNode v22.23.3で行い、`.nvmrc` の22に合わせる。過去の棚卸し・Review By期限の警告は今回の文書以外のものとして記録し、既存文書の日付を書き換えない。

今回の成果物は5つの設計文書とその検証記録。アプリの実装・runtime画面の撮影・子どもの試用・PWA更新・公開は未実施。製品正本は変更せず、実装へ移るときに必要な差分を同期する。
