# Authored world allocation review — static evidence and narrow change

Reviewed frozen `/private/tmp/sansu-authored-shoulder-c1/candidate` on 2026-10-12. Line references below refer to that candidate unless marked live. This was initially a static investigation: no browser, build, world compilation, memory probe or source edit was used to establish the allocation/coordinate findings. Root subsequently authorized only exact XZ index sharing, focused tests, and a separate three-state memory comparison. Measured comparison results belong to `/private/tmp/sansu-world-index-sharing/`; do not mistake the predictions below for those measurements.

## Findings supported directly by code and data

1. **One compiled world has duplicate search-index structures for identity XZ.** `worldDefinition.ts:243–244` always builds logical and physical bins independently for current-floor triangles. `bins` at 191–242 creates coarse arrays plus 16×16 fine Map/array lists for dense bins; coarse arrays remain retained. The existing expansion guard at 228–229 skips fine indexing at >=64 references per coarse candidate on average, but duplication below that threshold remains. `createSampler` retains both maps. Actual cell/point objects are *not* copied into each bin; bins store numeric triangle indices.
2. **The actual c1 data qualifies for exact sharing.** Lightweight JSON reads found zero indexed-vertex XZ mismatches across all 89,488 source floor triangles (10 floors, 50,180 serialized vertices), shoulder 6,615 triangles (two material floors), and cove apron 596 triangles. Their district turns and logical/world XZ origins are zero. Both legacy and source-shading original data have the same identity. Water interpolation uses the same rounded XZ expression for cell and point (`authoredWaterWorld.ts:131–133`); water/bed creation changes only Y (501–504). Bridge interpolation does the same (64–65), and its deck changes only Y (127–128). Thus source and these composition formulas support applicability; the implementation still checks each compiled triangle exactly rather than assuming identity by source ID. No runtime world was compiled to obtain this evidence.
3. **Definition and compiled geometry are retained together.** `compileWorldDefinition` deep-clones input at 107. `compileFloor` at 148–168 creates compiled cell/point/normal objects, copies index arrays, and creates triangle wrappers with two arrays of three vertex references. Anchor floors compile separately. `originalTriangles` shares existing triangle objects; it is not a third geometry copy. At 276–278 the anchor sampler is logical-only, and original sampling already reuses anchor/current sampling when their lists coincide. Do not describe these samplers as always duplicated.
4. **Additional support indices retain independent wrappers/buckets.** `authoredWorldAccess.ts:26–47` has a WeakMap keyed by compiled floors, creates per-triangle wrappers/3-point-reference arrays/bounds, and coarse triangle buckets (water also has a separate subset index). `authoredPlacementSupport.ts:72–85` creates another per-world triangle wrapper with logical/physical reference arrays and bounds; it is only needed after the early no-water return at 89–96. Both have bounded answer caches (16,384). They are not leaks solely because they use WeakMap, but their values stay live while cached worlds remain live. `authoredWaterCarving.ts:41–73` is another index over original/anchor source, restricted to carving scope in this source, so it is a smaller/stable-base candidate than the whole-world indices.
5. **Composition creates several large temporary worlds.** Shoulder compiles a support world and final world (`authoredShoulderWorld.ts:153,160`). Water compiles cut, optional bridge-support, dry, and final worlds (`authoredWaterWorld.ts:546,548,551,563`). Each successful bridge candidate also compiles at `authoredWaterBridge.ts:230`; its final `current` is omitted from the return at 235, then water may compile the same definition again for support. These stages perform validation/pruning and cannot simply be deleted. Cove compiles another full world at `authoredCoveWorld.ts:203`. Temporary world overlap and repeated cloning/indexing are credible peak contributors; exact retained paths/byte attribution were not proven by static reading.
6. **Domain caches can retain several distinct full worlds.** `authoredWorldFrame.ts:18–19,35–44,64–66` holds up to three final frames plus one land-extension world per immutable base. `authoredWaterFrame.ts:7–16` independently holds up to three upstream water worlds. A cove frame carries a new compiled world, so water upstream and final cove geometry can remain live together. This is distinct from the known driver Map issue, which was outside this review.

The object-heavy definition/compiled geometry, several samplers/support indices per world, and multiple retained worlds are concrete allocation candidates. Their relative shares of the reported ~869 MiB baseline or ~2 GiB LRU3 are hypotheses until measured. Repeated `structuredClone`, JSON fingerprint strings, triangle `slice/map`, bounds/range arrays, recursive freeze traversal and query Sets/polygons add construction/query churn; not all are retained after GC.

## Selected implementation and verification

Root authorized a narrow change in live `worldDefinition.ts:243`: build logical bins once; only reuse their exact reference for physical queries when every indexed triangle cell.x/z exactly equals point.x/z. Otherwise retain the old path. No thresholds, area/bounds rules, epsilon, candidate order, sampling math, floor contents, normals, support or product rules change. No new public API, cove cache, sampler refactor or geometry compaction was added. Existing uncommitted source-shading changes were preserved.

Focused verification: 26 tests PASS (20 `worldDefinition.test.ts`, 6 `worldFloorIndex.test.ts`); targeted ESLint PASS. The new behavioral case checks a mapped floor following identity floors. Existing differential tests exercise actual native05, transformed/mapped and legacy floors, highest/nearest-Y and water masking, ordered EPS seams, thin triangles, mutation isolation, and source-normal/material validation. First raw logs are preserved. Root owns shared full verification; this focused result is not a browser/app memory acceptance.

Expected but initially unmeasured: identity worlds avoid one complete current-floor coarse/fine index. This does **not** halve the whole heap: other samplers, support indices, geometry copies, stages and world caches remain. The exact before/after diagnostic uses three direct-domain states in separate processes, default heap, the original 99 local/six installed input closure, forced GC checkpoints, source/render/geometry/query/revision hashes, 768 MiB reserve and a 3 GiB retained stop. See the diagnostic report for observed deltas; after-call samples are not the true transient peak.

## Deferred alternatives

- **Exact cove-result cache is plausible, not implemented.** `composeAuthoredCoveWorld` has no compiled-result cache. Outer frame key includes drops/nextId (authoredWorldFrame 28), while water's key only includes plots/landmarks/keepsakes (authoredWaterFrame 9–13). Preview/commit may therefore return the exact same upstream water object but compile cove again. Cove revision inputs at 184–185 omit drops/nextId and place revision at `places.ts:183–184` derives geometry/membership, so the specific reported same-revision pair has a clear redundant path. A future cache must use exact immutable upstream identity **and full actual patch drawing/site/edge data plus output revision**, not physical-only fingerprint/profile name/public frame revision alone. Validate before reuse; fresh state-derived plan/places/reconciliation must still run. One cached result per upstream is sufficient to target exact repeated calls without an unbounded cache. Mutable caller profiles require fresh signatures, not shallow-freeze trust. Test receipt/drops/nextId variants, rendering-only profile changes, patch changes, state-dependent rejection/removal, and same public revision with unequal inputs. No memory saving is claimed without measuring.
- Reusing already compiled bridge support could remove one transient compile, but requires proof that returned definition and compiled `current` match after every candidate/rejection and validation stage. Defer from this small change.
- Shared logical/physical bounds alone would not prove identical fine-bucket expansion: `broad` also depends on projected triangle area. Exact XZ identity provides a simpler complete proof. No broad indexed-coordinate/bounds refactor is justified here.
