# 公開版「しま」の起動時間の切り分け

2026-09-19。対象は https://sansu-seven.vercel.app/ 、revision `1ae3cfa1d2ea7d3d4a6b17a28009be9a6b3b0a3c`。前回の歩行mesh最適化が配信済みの版を計測した。計測の前後でversion.jsonのrevision一致を確認。

[全計測report](report.json)・[CPU内訳](cpu-summary.json)・[CPU profile](owned-168h-repeat-cpu4.cpuprofile)・[7日分の島](owned-168h.png)・[いえから戻った画面](same-document-return.png)

## 条件と測定の境界

Mac上のPlaywright Chromium（headless/SwiftShader）、390×844。実際の公開JSを無変更で使い、専用の隔離ブラウザーに実UIでプロフィールを作成した。6家具と100件の同時刻の合成creditは公開版と同じソースのcommandLifeで作る。住人が歩いている場所への購入は正規ガードに従い、合成時計を進めて空くのを待つ。利用者の実データ・実端末には触れていない。

「初回描画」はLifeWorldのdata-renderedがtrueになった時刻で、GPUの画面提示そのものではない。「次の描画機会」はその後2回のrequestAnimationFrameが返った時刻。この差を無条件に利用者の待ち時間とみなさない。CPU4倍の条件は処理を意図的に遅くした診断であり、特定のスマホの再現ではない。GPU・画面表示の数値はheadlessのソフトウェア描画の影響を含む。

初期文書から起動し直す条件を比較した。最後の「いえ→しま」だけは同一タブ・同一文書内のUI操作からの経過時間で、JavaScript内のキャッシュが残る。各条件1回（前段の計測でも同程度の傾向）で、母集団のp95等ではない。

## 確認できた原因

1. **ページを開き直すと過去の行動を再計算する。** 7日分の直後再読込でも1.2秒の検証・再計算が繰り返される。replayCache.tsのキャッシュはMapで、文書を閉じると失われる。前回の最適化は個々の経路処理を速めたが、再計算する期間自体を減らしていない。
2. **成長速度の積分も住人の短い行動ごとに繰り返す。** CPU profileでeffectiveGrowthHoursが目立つ。simulation.tsの各時間区間でcompletionTimesを検証し、境界配列を作り直している。今回100件の合成creditを含む条件で確認したことで、前回の単純なCPU fixtureだけでは見えなかった費用が分かった。学習が多い全ケースの定量評価ではない。
3. **起動時に小さな見本画像を3Dから生成する。** LifeProductPreview/LifeResidentPortraitがWebGLを作ってPNG化する。今回の再読込ではtoDataURLが2回、合計約0.33秒。メモリー内のstillキャッシュは再読込で失われる。GL context生成開始から初回描画までは通常約0.56–0.60秒、CPU4倍で約1.13秒で、ここには見本生成・場面構築等の重なりがあるためPNG時間と単純加算しない。

初回描画後にも約0.9–1.0秒の長い処理が観測された。同じタブの戻りではPNG変換が0回でも残るため、これを全て見本生成のせいにしてはいけない。WebGLの初期描画やSwiftShader等の実行環境を含む残余であり、実機GPUでの追加計測対象。

## 今回の主因ではなかったもの

- 最初のworld getは約0.2–0.7ms。worldの生データ読取そのものは、この小規模fixtureの主因ではない。大量の学習履歴・古い端末のI/O全般を否定するものではない。
- 強制cold条件のresource転送は約1.12MB。通常条件はSW/HTTP cache利用。ネットワーク条件を遅くした試験ではないので、低速回線の影響は未測定。
- 全条件でruntimeAssets診断はnull、GLBリクエストは0件。今回追加したMeshy素材の配信負荷はこの公開版の遅延原因ではない。

## 次に直す優先順位

1. 正規recordの検証を維持しつつ、再生済み状態を再利用して毎回全期間をやり直さない仕組み。保存変更を伴うなら、版・所有者・action/credit境界・hashの不一致で安全に破棄できる派生キャッシュとする。学習履歴や所有物の削除で回避しない。
2. 開始時の住人/花の見本を事前生成または必要時生成にし、主島の表示を先に通す。
3. 成長速度の境界計算を同じ完了時刻列で再利用し、行動ごとの配列再生成を減らす。
4. 実端末のGPUで、初回描画後の長いフレームを計測する。

今回の範囲は診断。アプリや保存処理、本番配信は変更していない。
