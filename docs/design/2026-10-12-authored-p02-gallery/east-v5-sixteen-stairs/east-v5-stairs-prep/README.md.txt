## Visible geometry

Use shared tread/riser/boundary coordinates to build one closed staircase body directly. Horizontal upper tread triangles are the only stair walking surfaces; risers, side cheeks, rails, branches and underside are separate structural roles. A visibly continuous timber underside may slope, but it is never a walk floor or a hidden ramp. A naive .07 vertical copy of a stepped top can create opposing, overlapping vertical walls when the riser exceeds thickness; do not use that extrusion. Use a deliberately authored continuous underside below every tread and close each riser/side to it, keeping material thickness >= .07. Its added depth is explicit new structure, not a claimed preservation of the old slab envelope.

Keep the low front plateau, terrain-seamed entry width, actual native interior arrival and upper gallery endpoints. Shared attachment cross-sections must use the same coordinate arrays, not independently computed nominally coplanar surfaces. The source native interior remains unchanged. Connected new components may meet it with a measured positive structural joint; no Boolean repair is mandatory. Render any interface top only once, with an explicit common boundary. Branch supports attach under real treads/landings and into the same owner trunk/root: the v4 six support contacts cannot be reused as a clearance PASS after tread heights/underside change. Keep their raw measurements only as source provenance.

The whole view must first read as a wooden stair with distinct steps, a short usable gallery and visible load-bearing boughs. Keep the original timber material and curved-bough silhouette. Do not make an enormous box encircling the trunk, independently decorative steps, free columns or new grants. The fixed p3 house, l25 bench, original native trunk/crown/door and all four P02 owner transforms remain unchanged. Restore exact original four left-tree components in fixed35 context, as v4 did.

## Actual feet, not the body cylinder

`extract-feet.mjs` is a bounded, not-yet-run Node preparation. It instantiates only the fixed c1 Pokomoko plus eight actual villagers through their real source factories, at .7 rig × .45 visual scale. It does not construct any world, render, browse, project state or test the app. It exports used indexed foot vertices/triangles, root-local neutral coordinates, lower-half membership and the foot pivot transforms, plus actual current gallery swing poses (-.5..+.5), restoring each pose. Full projected feet and lower-hemisphere points are retained separately; the .244 body radius never substitutes for the sole.

The next small polygon diagnostic must use the same authored tread triangles, actual left/right pivots, ascent AND return headings and phase. A planted foot at a particular tread is checked against that tread's polygon/plane; report exact missing polygon support and edge margin, not only a bounding length. Swinging feet are checked for riser/body penetration rather than requiring ground under them. The sampled current gallery swing is a baseline diagnostic only, not a continuous motion proof. A new explicit stair pose must alternate planted feet, lift the swing sole over the actual riser with a stated reserve, and place it on the next tread. At least one planted foot remains on a real tread. Do not linearly slide the full actor along an imaginary diagonal support plane. Retain raw failures and continuous-angle critical extrema before claiming motion clearance.

The 16/18 candidates stay HOLD until both neutral/dynamic foot support and fixed-source body/door/head clearance are checked. A changed route or landing is an explicit candidate change, not an unrecorded optimizer. No baseline floor/door exclusion or tolerance increase is allowed.

## Runtime boundary deferred

Current `GrowingLife.tick` gallery motion linearly interpolates XYZ, rotates feet ±.5 and calls `alignActorContact` once for the entire visual subtree. It cannot independently plant two feet on different treads. Source design must therefore expose ordered tread IDs, tread polygons/planes, riser edges, lower/upper landing IDs, explicit entrance and stepping targets. The future renderer and physical query use the SAME visible triangles. A pose path is a body/foot trajectory, not an invisible floor.

Default ground queries and site.support remain unchanged. Elevated owner-use surfaces require explicit role/ID within the same world. The gallery receipt currently requires `gallery.point.y - layout.heightAt(gallery.point) > .8`; changing the default ground to the upper surface would erase actual use. Revision must bind the real four owners/source/shape. Move/store/separation must use the existing place revision invalidation and old entrance evacuation, and retain prior use history. No app contract is implemented by this preparation.
